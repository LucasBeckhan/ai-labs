# 06 — LLMOps / AI Infra 15 题（数据工程师的 AI 平台方向）

> 数据平台岗越越来越多的 AI 负载问题（模型服务、GPU、RAG 数据链路）。这 15 题基于 llmops-labs 的实测实验整理——**每题你都有亲手跑过的对应物**，这是和其他候选人最大的区别。标 ★ 必问。

## A. 模型服务与推理（5 题）

### Q1. ★ LLM 应用上 K8s 和普通应用有什么不同？

【参考回答】三点：① **依赖重**——模型权重 GB 级，要么进镜像（分发慢）要么外置成服务（我选后者：模型服务独立部署，应用容器轻量）；② **响应慢且长**——推理秒级起步、流式输出，readiness 探针用轻量路径、超时给足，负载均衡要考虑长连接；③ **指标体系不同**——除 QPS/延迟外，核心 SLI 是 TTFT（首 token 延迟）、TPOT（每 token 时间）、token 吞吐、显存利用率、**成本（每千次请求的 token 费用）**。

【追问链】模型服务怎么扩容？（GPU 利用率 + 队列深度做 HPA/KEDA；KV Cache 占满时扩容不是加副本而是加显存）→ 你测过推理延迟吗？（llmops-labs Lab 08 实测：串行 85 tok/s、并发 1.52x 提升——CPU 场景都成立，GPU 上 vLLM 连续批处理把倍数拉大一个量级）

【动手印证】llmops-labs Lab 01（推理参数/体感）+ Lab 08（吞吐对照实验）。

### Q2. vLLM 为什么快？显存怎么估算？

【参考回答】两大机制：**PagedAttention**——KV Cache 像操作系统分页一样管理，传统按最大长度预分配的碎片率 60–80%，分页后接近满载，同显存并发翻几倍；**连续批处理**——新请求任意 decode 步骤插队，GPU 始终满载。**估算方法**（面试先给公式再带假设）：权重 = 参数量 × 字节数（7B FP16 = 14GB）；KV Cache 每 token = 2 × 层数 × 隐藏维度 × 字节数（7B ≈ 512KB/token）；10GB 剩余显存 ÷ 2000 token/请求 ≈ 10 路并发，PagedAttention 后再乘利用率倍数。

【追问链】prefix caching 是什么？（公共前缀的 KV 直接复用——RAG 场景 system prompt 固定，直接省钱省时延）→ 你们推理服务监控什么？（TTFT/TPOT/显存/队列深度，llmops-labs Lab 06 的 /metrics 骨架扩展）

【动手印证】llmops-labs Lab 08（估算练习 + 吞吐对照实测）。

### Q3. GPU 在 K8s 上怎么管理？时间切片的风险？

【参考回答】device plugin 使 GPU 成为可调度扩展资源（`nvidia.com/gpu: 1`），GPU 节点打污点防普通任务抢占；整卡浪费时 time-slicing 共享（**隔离弱**：一个 Pod 打满 SM 拖累邻居）或 MIG 硬隔离；演进方向 DRA。**监控**：DCGM exporter → Prometheus（SM 利用率/显存/XID 错误告警）。

【动手印证】k8s-labs Lab 06（污点模拟 GPU 节点池）。

## B. RAG 与评估（5 题）

### Q4. ★ RAG 链路是什么？质量瓶颈在哪？

【参考回答】离线：文档 → 分块 → 嵌入 → 向量库；在线：查询嵌入 → top-k 检索 → 拼 prompt → 生成。**瓶颈多数在数据侧**：分块策略（400 字符经验值）、嵌入模型语言匹配（中文用 bge-m3）、检索召回。**一句话立场**：RAG 首先是数据质量工程——这话从数据工程师嘴里说出来天然可信。

【追问链】中文嵌入模型怎么选？多语言模型 bge-m3 vs 中文专用 bge-large-zh？（场景：多语言混排选 m3）→ 块大小怎么定？拍脑袋吗？（不——评估集量化）

【动手印证】llmops-labs Lab 03（全链路 + TOP_K 实验）。

### Q5. ★ 你怎么评估一个 RAG 系统的效果？

【参考回答】三层指标：**检索层** Recall@k（依据文档是否被检回）、**生成层** 忠实度（回答是否只基于检索内容）与要点完整性、**安全性** 越界拒答（知识库没有的要老实说没有）。**方法论**：建 20~50 题评估集（换一种问法，不抄原文），任何参数/模型变更都跑一遍——**没有评估就没有 LLMOps**。实测案例：TOP_K 3→6，忠实度 60%→80%；同时发现 LLM 输出随机性导致单次评估有噪声（多跑取稳定结论）。

【追问链】幻觉怎么治？（拒答失败实测：0.5B 模型不遵守"没有就说没有"——属于模型能力问题，解法是相似度阈值兜底 + 更强模型，不是调 RAG 参数）→ 忠实度怎么自动化？（关键词校验是下位替代，规模化用 LLM-as-judge，但要抽检 judge 稳定性）

【动手印证】llmops-labs Lab 04（评估流水线 + 全部实测数字）。

### Q6. RAG 生产化的坑你踩过哪些？

【参考回答】实测清单：① **不设 max_tokens 的无限生成**（0.5B 模型单次跑出 1.8 万 token 卡死流水线——生产 max_tokens+超时标配）；② 中文乱码双端性（数据写入端与读取端都要 utf8mb4）；③ 向量库集合名/持久化的工程细节；④ 网关调用必须带 provider 前缀。**面试价值**：这四个坑全是"真跑过才踩得到"的——比背 RAG 原理更能证明实操。

【动手印证】llmops-labs Lab 03/04/05 的"常见坑"章节。

### Q7. RAG、微调、prompt 工程怎么排序？

【参考回答】按边际成本排：**prompt（零成本，实测 few-shot 一行解决 Text2SQL 纠错）→ RAG（知识注入，可更新可溯源）→ 微调（行为/格式固化，成本高）**。微调不擅长注入知识——知识会过期，RAG 随时可换。**案例化表达**：Text2SQL 优化阶梯实测（重试无效 → 升级 1.5B 无效 → few-shot 一次成功），"我们习惯性地觉得模型不行就换模型，但实测 prompt 一行字解决了，成本是零"。

【动手印证】llmops-labs Lab 05（完整优化阶梯实录）+ Lab 07（LoRA 路线）。

## C. 网关与治理（3 题）

### Q8. ★ 为什么要 AI 网关？架构长什么样？

【参考回答】直连模型的痛点：key 散落、限流各自为政、成本无法归因。网关四职责：**统一协议**（OpenAI 兼容是事实标准）、**模型别名路由**（应用写别名，后端随时替换/灰度）、**虚拟 key**（按团队发放，RPM/预算双层限制，key 落库网关无状态）、**用量观测**（token 归因到人）。实测：`rpm_limit=3` 的 key 第 4 发即 429；Postgres 存 key，网关可水平扩展。

【追问链】网关成了单点怎么办？（无状态多副本 + LB）→ 降级策略？（主模型超时切备用别名，网关层 failover）

【动手印证】llmops-labs Lab 02（完整网关实验）。

### Q9. token 成本怎么治理？

【参考回答】三层：**计费归因**（虚拟 key 按团队记账，模型价格表算 spend）；**降本手段**（缓存公共前缀、小模型路由——分类/抽取类请求路由到 0.5B 级别、prompt 精简、max_tokens 收紧）；**预算管控**（月度 max_budget 超限降级或拒绝）。**数据视角**：token 账单和数仓成本账单是同一个治理思想——先有度量再有治理。

### Q10. LLM 应用的安全防线怎么做？（SQL 场景）

【参考回答】Text2SQL 三层防线，**权限层最可靠**：只读账号（GRANT SELECT）→ 应用层白名单（只放行 SELECT + 强制 LIMIT + 超时）→ prompt 层约束（提示不是防线）。**实测证据**：模型对"删除所有用户"真的生成 `DELETE FROM users;`——被护栏拦截。把"prompt 是提示不是防线"这句讲清楚，就知道你是真跑过还是背过。

【动手印证】llmops-labs Lab 05（护栏拦截实录）。

## D. 数据工程师做 AI 平台的定位（2 题）

### Q11. 数据工程师在 LLM 时代的独特价值是什么？

【参考回答】三个"天然优势区"：① **RAG 就是数据工程**——分块/清洗/索引/质量监控全是数据链路的老手艺；② **评估就是数据质量体系**——评估集、回归、阈值告警与 DQC 同构；③ **LLM 应用的数据面**（向量库运维、embedding 管道、知识库更新机制）没人比数据工程师更熟。**反面也要说**：缺的是模型层（训练/推理引擎）深度——所以我的学习路径是应用层→平台层→推理层→模型层（llmops-labs README 的四层地图）。

### Q12. 你们平台的 AI 负载和数据负载怎么共存？（混部题）

【参考回答】K8s 统一底座：GPU 节点池打污点专用（推理服务常驻 + 训练 Job 排队）；数据作业（Spark/Flink）在 CPU 节点池错峰混部；统一监控（Prometheus + DCGM）、统一发布、统一 key/配额管理（AI 走网关、数据走调度平台）。**加分**：提 Kueue/Volcano 的队列语义映射 YARN 队列习惯。

【动手印证】k8s-labs Lab 06（污点/节点池）+ Lab 09（HPA）。

## E. 综合与趋势（3 题）

### Q13. Agent 的本质是什么？和 Workflow 怎么选？

【参考回答】Agent = 模型在循环里调用工具（执行 SQL/查库/检索）并观察结果决定下一步——**Text2SQL 的"生成→执行→报错回传→重试→升级"就是最小 Agent**（llmops-labs Lab 05 实测过完整的）。选型：路径确定用 Workflow（可控可测），路径发散用 Agent（灵活但不可控）。生产原则：Agent 的每个工具都要有护栏（Lab 05 的白名单思路）。

### Q14. MCP / Function calling 了解吗？

【参考回答】Function calling 是模型输出结构化调用请求的能力（各家协议趋同）；**MCP** 是把工具/资源/提示词标准化暴露的协议（类 USB-C：工具服务一次实现，多模型多应用复用）。数据工程师的机会：把公司数据源（SQL/数仓/指标平台）封装成 MCP server，让所有 Agent 安全地查数——护栏思路（只读账号+白名单）原样适用。

### Q15. 你们下一步会在 AI 平台上做什么？

【参考回答】（三面考视野与规划，按自己情况答）框架：**短期**——RAG 知识库全量化（评估集护航）+ 网关统一接入公司全部模型；**中期**——模型服务上 K8s GPU 池（vLLM + KEDA 弹性）、推理观测（TTFT/成本/质量三线看板）；**长期**——Agent 平台（工具市场 + 护栏体系）、特征/知识库的统一元数据管理。**收尾**：每一步都先建评估和度量——这是我从数据平台带过来的方法论。

## F. 进阶追问库（5 题）

### Q16. RAG 的高级检索：混合检索与 rerank 是什么？
向量检索（语义）+ BM25（关键词）双路召回 → RRF 融合 → **rerank 模型**（cross-encoder 对 query-doc 逐对精排，如 bge-reranker）取 top-N。实测收益：rerank 能把 TOP_K 压力减小（召回 50 精排取 5，优于召回 6）。Graph RAG（知识图谱增强）了解概念即可，工程落地尚早。

### Q17. Agent 的记忆机制怎么做？
短期记忆 = 上下文窗口（对话历史，超长要做摘要压缩）；长期记忆 = 外部存储（向量库存对话摘要/事实，按相关性召回）。**数据视角**：这就是"会话级 ODS + 用户级 DWS"的翻版——记忆的分层、过期（TTL）、质量（噪声清理）全是数据工程问题。

### Q18. 开源模型还是商用 API？
决策矩阵：数据敏感性（私有数据 → 本地/私有云部署开源模型）、成本结构（API 按 token 付费 vs 自建 GPU 固定成本——量大且稳定才自建）、能力要求（复杂推理 → 商用旗舰模型仍领先）。**混合路由**（Lab 02 网关）是现实答案：简单任务路由开源小模型，复杂任务走 API——成本可降 70%+。

### Q19. 微调的训练数据怎么构建？
来源：线上 badcase（Lab 04 评估的失败案例）+ 人工标注 + 强模型蒸馏（用 GPT-4 级模型生成初稿人工审核）。质量原则：**输出必须是你真正想要的样子**（格式/风格完全符合生产要求）、多样性覆盖真实分布、去重。规模：行为对齐几百~几千条起步；配留出集防过拟合（Lab 07）。

### Q20. 多模态（图像/语音）会改变数据链路吗？
会但骨架不变：图像→向量（CLIP 类嵌入）入向量库、语音→ASR→文本、检索同样 top-k。数据工程师的增量是**多模态数据的存储与管道**（对象存储 + 元数据 + 嵌入管道），检索与应用层框架不变。

# 追问实录：RAG 项目的完整模拟对话

**面试官**：你说做过 RAG 知识库，回答质量怎么保证的？

**候选人**：建了评估集——把真实用户会问的问题 + 标准答案要点 + 答案出处整理成 JSONL，写了个评估脚本跑三个指标：检索命中率（出处文档有没有被检索进 top-k）、忠实度（回答是否包含要点）、越界拒答（知识库里没有的问题要老实说没有）。任何参数改动都跑评估集对比。

**面试官**：评估集多少题？怎么来的？

**候选人**：起步 20 题、目标 50+。来源三类：真实用户高频问题、每类知识点的代表问题、**故意设计在知识库之外的越界问题**。一个原则：评估题不抄知识库原文——换一种问法，否则检索永远 100%，指标没有区分度。

**面试官**：检索条数你怎么定的？为什么是 6？

**候选人**：跑出来的。TOP_K=3 和 6 各跑评估集：忠实度 60% vs 80%——3 的时候部分问题的关键块进不了上下文。但也发现 TOP_K 不是越大越好：超过 6 之后引入噪声，模型开始被无关内容带偏，而且长 prompt 的成本和延迟都在涨。**结论是"评估集能给出参数的甜点区"，这个数字对我们知识库成立，换知识库要重测。**

**面试官**：忠实度 80% 里丢的那 20% 是什么问题？

**候选人**：分层归因过：一道是检索问题（关键块没进 top-k，要上 rerank 或混合检索）；一道是生成问题——检索到了但 0.5B 模型换了个说法没覆盖要点，关键词校验判了不通过——这里我发现了**评估本身的噪声**：LLM 输出有随机性，单次评估同一题可能一个对一个错，所以结论要多轮取稳定值。生产的解法是把关键词校验升级成 LLM-as-judge。

**面试官**：模型幻觉过吗？怎么治？

**候选人**：实测有——越界题（珠峰高度）0.5B 模型会"顺着上下文格式编"。我归因为模型能力而不是检索问题：检索指标正常但拒答 0/1。解法按成本排：prompt 强化（效果有限）、检索相似度阈值兜底（低于阈值直接拒答，最有效）、换更大模型。**要点是把"检索挂了还是生成挂了"归因清楚，否则调错方向。**

**面试官**：生产上这套服务怎么部署的？监控什么？

**候选人**：FastAPI 容器化部署在 K8s，/metrics 暴露请求数和累计延迟，Prometheus 用注解发现自动抓。监控三条线：调用量（QPS）、延迟（平均与 P95）、**拒答率**——拒答率突增通常意味着知识库没覆盖新问题，是"该补知识库了"的业务信号，不只是技术指标。

**面试官**：如果知识库每天有 10 万篇文档更新，你的架构哪里要改？

**候选人**：三个升级：① 嵌入计算从"启动时全量"改成增量管道（按文档变更流更新向量库，做删改的向量同步）；② 单机 chromadb 换分布式向量库（Milvus/ES）；③ 检索加 rerank 层，因为文档多了之后 top-k 召回质量下降。但评估驱动的方式不变——每次架构变更还是跑同一套评估集对比。
