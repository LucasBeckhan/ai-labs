## A. Spark 核心（8 题）

### Q1. ★ Spark shuffle 的完整过程？和 MapReduce shuffle 的区别？

【面试官为什么问】Spark 调优的一半在 shuffle，这题决定后面调优题的可信度。

【参考回答】Shuffle 划分 Stage 的边界（宽依赖处），本质是**按 key 重分布数据**。流程：上游 Stage 每个 task 按 partition 写出数据文件（hash 分桶到下游分区数）+ 索引文件；下游 task 通过 MapStatus 获取位置后拉取。演进要讲三代：**Hash Shuffle**（每 task 每 partition 一个文件，文件数爆炸）→ **Sort Shuffle**（每个 task 一个按分区排序的数据文件 + 索引，Spark 1.6 后默认）→ **Tungsten-Sort / 序列化排序优化**（off-heap 二进制数据直接排序，减少序列化开销）。和 MR 的区别：MR shuffle 必须 sort（归并语义），Spark 的 sort 只是溢写手段；MR 中间结果落 HDFS？不落（也走本地磁盘），但 Spark 有 pipeline 化（窄依赖不落盘）+ 血缘容错。

【追问链】shuffle 文件过多的问题怎么解？（repartition 合并 / AQE 自动 coalesce）→ 数据落盘在哪配？（spark.local.dir，K8s 上挂本地 SSD——呼应 01 篇 Q9）

【动手印证】k8s-labs Lab 10 的 Spark on K8s 环境；简历里的 spark.shuffle 参数要能报出你调过的具体值。

### Q2. ★ Spark 内存模型？executor 内存怎么算？

【参考回答】1.6+ 统一内存管理：`executor 总内存 = spark.executor.memory（堆内） + spark.executor.memoryOverhead（堆外，默认 0.1×堆）+ offHeap（如启用）`。堆内 = Reserved(300MB) + **Unified（Execution + Storage 共享，默认 0.6）** + User Memory（0.4，放用户数据结构）。Execution 不够可借 Storage 的（反向只能借一半），这是"cache 把执行内存挤爆"问题的根源。**K8s/YARN 配置法**：容器 limit = memory + memoryOverhead + 10% 余量，配少就是 137。

【追问链】storage 和 execution 借用规则？（Execution→Storage 可全借，Storage→Execution 最多一半，且 Storage 借出的可被强制回收、Execution 借出的不可）→ 你的 executor 配多大、为什么？（给真实案例：4C8G+2G overhead，依据是单个 task 处理分区大小 ×2~4 倍余量）

【动手印证】k8s-labs Lab 01（JVM 容器内存感知）+ Lab 05（cgroup limit 语义）。

### Q3. ★ 数据倾斜的原因与全套解决方案？（必问中的必问）

【面试官为什么问】这道题的深度=你的真实项目深度。答两招的通常 20k；能讲出"先定位、分层治理、每招的代价"的才是 40k。

【参考回答】
**定位**：Spark UI 看 Stage 的 task 最大/最小处理量与耗时差距（max≫median）；或 `df.groupBy(key).count()` 采样 top key。
**根因**：key 分布不均（空值、热点：默认值/大主播/大 V/某城市）导致单 partition 数据/计算集中。
**方案矩阵（按代价从低到高）**：
1. **过滤**：确认无意义的倾斜 key（如脏数据 null）直接过滤——最便宜；
2. **两阶段聚合（加盐）**：groupBy 类，key 加随机前缀 1w 份局部聚合 → 去前缀全局聚合，把 N 次大聚合摊薄；
3. **广播 Join**：小表 join 大表倾斜 → `broadcast()`，代价是 driver/executor 内存装得下（<200MB 谨慎）；
4. **倾斜 key 拆分 join**：大表倾斜 key 单独捞出来扩 N 倍随机数，另一表相应膨胀 join，再 union 回去——**代码复杂度最高，只救核心链路**；
5. **AQE 自动处理**（3.0+）：`spark.sql.adaptive.enabled=true` + `skewJoin`，运行时按统计自动拆分倾斜分区——**先看 AQE 能解决多少，再手工补刀**，顺序别反；
6. **Flink 侧对应**：keyBy 热点打散（key 加盐 + 二次聚合）、mini-batch 聚合、LocalGlobal 优化。
**收尾量化**：大促作业 AQE 解决 70%，count(distinct) 类手工两阶段，整体 68min→22min——把数字换成你的。

【追问链】count(distinct) 为什么天然倾斜？（同一 key 全部进一个分区做去重）→ 亿级 UV 精确去重怎么优化？（两阶段 distinct 或 bitmap：Hive 用 trans_wit，Doris/CK 原生 bitmap/Roaring）→ 加盐对排序类窗口为什么无效？（窗口按原 key 语义，不能打散——只能先聚合出中间态再开窗）

【动手印证】`lab-数仓小实验/03-连续登录.sql` 尾部思考题 3 即倾斜点。

### Q4. Spark 3.0 的 AQE 解决了什么三个问题？

【参考回答】运行时根据 **shuffle 统计信息**重优化：① **动态合并小分区**（reduce 后合并，治海量小 task）；② **动态切换 join 策略**（运行时发现表足够小，sort-merge join 转 broadcast——计划期估错也不怕）；③ **动态优化数据倾斜**（skew join：倾斜分区按阈值拆成多个子分区分别 join）。前提：非 streaming、有 shuffle、map 端统计已生成。

【追问链】AQE 和 DPP（动态分区裁剪）的区别？（AQE 运行时重规划，DPP 是计划期用维表分区值裁剪事实分区——都开，不冲突）

### Q5. Spark shuffle 读不到上游文件 / FetchFailed，怎么排查？

【参考回答】FetchFailed 本质=**executor 挂了导致上游 shuffle 文件丢失**。排查链：看挂掉的 executor 死因（OOM 137 → 内存配置/倾斜；被 K8s 驱逐 → 资源竞争；磁盘满 → shuffle 目录）→ Spark 的容错是重算丢失分区（`spark.shuffle.maxRetries`、`spark.stage.maxConsecutiveAttempts`）。**K8s 特有**：executor 被 kubelet 驱逐时死得比 YARN 突然，本地盘 shuffle 全丢——所以 shuffle 目录必须挂本地 SSD emptyDir 而不是容器 overlay fs，且资源 requests 要写实。

【动手印证】k8s-labs Lab 05（驱逐实验）+ 01（容器磁盘语义）。

### Q6. Spark 有哪些 join 策略？怎么选？

【参考回答】五种：Broadcast Hash Join（小表广播，首选）、Shuffle Hash Join（大+中，内存够）、Sort Merge Join（两大表默认，需排序）、Cartesian、Broadcast Nested Loop（不等值）。**选择器**：Catalyst 按 hint + 统计信息自动选，`spark.sql.autoBroadcastJoinThreshold`（默认 10MB）控制广播阈值。**调优实践**：统计信息不准导致该广播没广播 → analyze table + 显式 hint；AQE 的动态转广播（Q4）兜底。

### Q7. 小文件问题怎么治理？

【参考回答】危害：元数据压力（NameNode/湖格式 manifest）、调度开销、查询 planner 变慢。治理分**预防**（写前 repartition/coalesce 到合理大小 128~256MB、按分区预估并行度、AQE coalesce）和**存量治理**（定时 compaction 任务：湖格式跑 Paimon/Hudi compaction 或 Hive 重写； iceberg rewrite_data_files）。**量化**：我们某表从日均 8w 文件压到 3k，查询 planner 时间从分钟级到秒级。

### Q8. 缓存（cache/persist）什么时候用？有什么坑？

【参考回答】用：被多次 action 复用的中间结果（迭代式 ETL、机器学习）。坑：① cache 的是**血缘计划**不是数据快照，上游重新计算时 cache 失效场景理解错；② Storage 内存不足会丢缓存重算（反而更慢）；③ unpark 不释放导致 executor OOM。规范：`persist(StorageLevel.MEMORY_AND_DISK)` + 用完 `unpersist()`；Kryo 序列化减小缓存体积。

## B. Hive / SQL 引擎（3 题）

### Q9. Hive 的 Map/Reduce/Strict 模式与谓词下推？

【参考回答】分区裁剪 + 谓词下推是两件事：分区裁剪靠 `WHERE dt='...'` 命中分区列（Strict 模式强制分区过滤，防全表扫）；谓词下推把过滤推到存储层（ORC/Parquet 的 stripe/index 只读命中的行组）。**答题延伸**：ORC 的三种索引（行组级统计/bloomfilter），"为什么大表查询快"的底层答案。

### Q10. Hive SQL 转 MapReduce/Tez/Spark 的原理？什么 SQL 跑不动？

【参考回答】Antlr 解析 AST → 语义分析生成 QueryPlan → 逻辑优化（谓词下推/列裁剪/MapJoin 转换）→ 物理计划。跑不动的典型：**复杂窗口嵌套**（多级 over 不下推）、**笛卡尔积**、**udaf 里带状态的自定义聚合在 vectorization 失效**。讲一个真实案例：某个三层窗口+UDF 的任务改写成两段临时表后从 3 小时到 20 分钟。

### Q11. Hive 小表 join 大表的 MapJoin 原理与坑？

【参考回答】小表全量读入内存建 hash 表，广播到每个 map task，大表 map 端完成 join（无 shuffle）。坑：① 阈值判断用的是**压缩后大小**估计，解压后可能爆内存；② 大量小文件作为小表时 task 加载 OOM；③ `hive.auto.convert.join.noconditionaltask.size` 的合并逻辑。K8s/YARN 上配 executor 内存时把这个峰值算进去。

## C. Flink 核心（6 题，实时数仓必问）

### Q12. ★ Flink 的 checkpoint 原理？exactly-once 怎么实现？

【参考回答】**Chandy-Lamport 分布式快照**：JobManager 的 CheckpointCoordinator 周期性向 source 注入 **barrier**；barrier 随数据流向下游，算子收到所有输入的 barrier 后**把状态快照写进 StateBackend**（对齐 barrier 期间不处理后续数据——at-least-once 语义），source 端还要**重放**能力（Kafka offset 快照进状态）。Exactly-once 完整版 = barrier 对齐 + **两阶段提交**（TwoPhaseCommitSinkFunction：预提交 → checkpoint 完成 → commit；Kafka producer 事务实现）。**恢复**：从最近成功的 checkpoint 重启，source 回放 offset，下游靠事务回滚未提交数据。

【追问链】unaligned checkpoint 是什么？（barrier 越过在途数据直接前进，把在途数据存进快照——反压时大杀器，1.11+）→ state backend 选型？（HashMap（小状态快取快）→ RocksDB（大状态增量 checkpoint）；我们 XX TB 状态用 RocksDB 增量）→ checkpoint 失败的常见原因？（barrier 对齐超时=反压；RocksDB 落盘慢；反压导致 source 快照超时）

### Q13. ★ Flink 反压怎么定位与解决？

【参考回答】**定位**：Flink WebUI 的 backpressure 标签（高/低比例）+ Flame Graph 火焰图直接看热点栈（1.13+ 内置）；常见根因：下游 sink 限速（Kafka 生产者 batch、JDBC 写入慢）、窗口计算过重（窗口内数据量暴涨）、序列化开销、资源不足。**解决**按因：sink 侧批量+并发；算子侧提高并行度/算子链拆开（disableChaining 便于隔离）；资源侧 slot 数与内存。**数据视角**：反压 → checkpoint 超时 → 频繁失败重启的连锁，所以我们把"反压时长>10min"设为 P1 告警。

【追问链】反压时为什么 checkpoint 超时？（barrier 排队在积压数据后面）→ 你们怎么发现反压的？（Flink metrics 的 outPoolUsage/inPoolUsage + 时延标记）

### Q14. Flink 的维表关联有哪些方案？各自优劣？

【参考回答】四招：① **预加载/广播**（小维表全量进内存，定时刷新——最快，容量受限）；② **异步 IO（AsyncFunction）**（查 HBase/Redis/HTTP，吞吐高，注意超时与缓存：Caffeine + TTL）；③ **Broadcast State**（维表变更流广播出去，本地 join——CDC 场景标准做法）；④ **Temporal Table Join**（版本化维表，基于事件时间关联"当时"的版本——严格 exactly-once 的正确性最佳，常配 CDC 入湖表）。**实时数仓实践**：大维表走 ③/④，小维表走 ①，组合拳常见。

【追问链】维表更新了怎么办？（广播流 + 版本号；或湖表 temporal join 的 changelog）→ 异步 IO 的乱序怎么处理？（CompletableFuture 结果按到达顺序回填，注意 watermark 语义）

### Q15. Flink 状态管理与过期（TTL）？

【参考回答】Keyed State（Value/List/Map/Reducing）+ Operator State；RocksDB 增量 checkpoint 支持超大状态。**TTL**：`StateTtlConfig`（更新/访问时刷新 + 过期清理策略：默认惰性删除 + 压缩时清理），典型用途：UV 状态、去重 state、join 缓存——**不设 TTL 的 state 是定时炸弹**（状态越涨越大，checkpoint 越来越慢直到失败）。我们状态从无 TTL 的 40TB 治理到 8TB 的真实经验。

### Q16. Flink CDC 是什么？和 Kafka Connect 的区别？

【参考回答】Flink CDC 基于 Debezium 引擎封装成 Source 连接器，直连 MySQL binlog/PG 逻辑复制，**增量+全量一体**（无锁全量读取），直接在 Flink 里做 ETL。区别：Kafka Connect 是独立进程栈（需要额外运维 Kafka+Connect 集群），Flink CDC 融进计算作业、支持整库同步到湖表（Paimon schema evolution）。**实时数仓选型**：简单入 Kafka 队列 → Debezium+Connect；做"实时入湖+自动建表" → Flink CDC Pipeline（2.4+ 的整库同步写法）。

## D. Kafka（3 题）

### Q17. ★ Kafka 为什么快？怎么保证不丢消息？

【参考回答】快四件套：**顺序写**（append-only log）、**页缓存**（读写都走 page cache，不主动管理堆内缓存）、**零拷贝**（sendfile 数据不进用户态）、**批量与压缩**（producer batch + lz4/zstd）。不丢分三段看：**producer**（acks=all + retries + 幂等 enable.idempotence 防重试乱序）；**broker**（副本 ≥3、min.insync.replicas=2、unclean.leader.election=false）；**consumer**（手动提交 offset，处理完再提交；事务性读-处理-写配 Flink 两阶段提交）。**代价要说**：acks=all + 同步刷盘会显著降吞吐——我们的取舍是"acks=all + 依赖副本不刷盘"，因为单机故障已由副本兜底，机房级灾难接受 RPO>0。

【追问链】rebalance 的坑？（consumer 组扩缩容触发 STW 式 rebalance → 用 static membership + cooperative-sticky 协议）→ 消息积压怎么处理？（先看消费端吞吐瓶颈 → 加分区+并行度 → 历史积压按 key 分段旁路处理）

### Q18. Kafka 的 ISR 是什么？HW 和 LEO 的区别？

【参考回答】ISR = 与 leader 保持同步的副本集合（落后超过 replica.lag.time.max.ms 被踢出）；HW（High Watermark）= ISR 中最小 LEO，消费者只能读到 HW 之前的消息；LEO = 每个副本的下一条写入位置。**追问预警**：为什么 consumer 只能读 HW 之前？（保证读到的消息已在多个副本持久化，leader 切换不丢）。

### Q19. Exactly-once 语义端到端怎么理解？

【参考回答】分三段：source 可重放（Kafka offset）+ 计算状态一致（checkpoint）+ sink 可事务/幂等（Kafka 事务、JDBC upsert、湖表提交）。**陷阱题**：Kafka 的 EOS 只覆盖 Kafka→Kafka；写到外部系统要靠幂等或 XA——把"端到端"拆开讲是资深和初级最大的区别。

## E. HBase / 存储引擎（2 题）

### Q20. HBase 的读写路径？为什么读比写慢？

【参考回答】写：WAL（HLog）→ MemStore（内存跳表）→ 满了 flush 成 HFile（LSM）；读：**MemStore + BlockCache + 多层 HFile 合并查找**（BloomFilter 过滤无关 HFile）→ 读时归并。慢的原因就是 LSM 的读放大：文件数越多读越慢 → **compaction**（minor 合并小文件 / major 全量合并）平衡读写放大。RowKey 设计（散列避免热点、长度 10~100B、反转/加盐）是面试必追。

【追问链】Region 热点怎么办？（预分区 + rowkey 散列；讲一次大客户 rowkey 热点的治理）→ 和 HDFS 的关系？（HFile 落 HDFS，多副本，所以 HBase 高可用靠 HDFS 而不是 Region 副本）

### Q21. Hive 数仓里的 HBase 和直接用 HBase 有什么区别？（考察场景理解）

【参考回答】数仓用 HBase 通常做**在线维表/用户画像 KV 查询**（低延迟点查），数据由离线任务批量灌入（bulkload 生成 HFile 再 load，避免写放大）；直接用 HBase 是 OLTP 型业务库。**架构上要讲清 bulkload**：MR/Spark 生成 HFile → completebulkload 上线，绕过 WAL+MemStore——批量导入的正规姿势。

## F. 综合工程（3 题）

### Q22. 离线任务大面积延迟，你怎么应急？

【参考回答】**先分级再动手**：定位瓶颈层（调度平台看最晚就绪 vs SLA 基线）→ 分类：资源不够（扩容/抢占低优先级）、数据暴涨（上游异常先堵源头）、任务失败连锁（重跑拓扑关键路径）。**止损优先级**：老板看板 > 核心链路 > 长尾报表；允许降级（昨日快照 + 注释声明）。**事后**：把这次暴露的单点进基线治理。所有动作要能讲出"决策依据"。

### Q23. 你的集群资源利用率怎么提升的？（成本治理题）

【参考回答】三板斧 + 数字：① **错峰**（离线高峰挪到低峰，与在线服务错开）；② **队列配额治理**（按"产出价值/资源占用"排序砍尾巴）；③ **弹性**（K8s 混部/spot 节点跑可重试任务）。示例数字：利用率从 35% → 62%，月成本降 28%。**方法论收尾**：先建"作业级成本账单"（资源×时长），没有账单的治理都是耍流氓。

### Q24. 湖仓/引擎选型你的方法论？（承上启下题，答案延伸到 04 篇）

【参考回答】**场景 → 约束 → 验证**三段法：先写清业务诉求（时效/更新/成本），列硬约束（团队技能/现有组件/云绑定），再 POC 三组数据集对比。反对"社区火什么上什么"——每个组件每年运维成本是隐性数字。示例：Paimon vs Hudi 我们选 Paimon 的三条理由（追加+更新混合负载、Flink 原生集成度、运维简单），以及放弃 Hudi 的两条代价（Compaction 策略调优复杂、Python 生态弱）。

## G. 进阶追问库（8 题）

### Q25. ★ YARN 的架构与调度器？（迁移 K8s 话题的必问基础）
RM（全局资源调度）+ NM（节点管理）+ AM（应用生命周期）。调度器：**Capacity Scheduler**（队列保底+弹性借资源，生产主流）、Fair Scheduler（公平份额）。核心参数：队列 capacity/max-capacity、user-limit、AM 资源占比。**迁移 K8s 的映射**：队列 → namespace+ResourceQuota、标签 → 污点/亲和、本地化 → 拓扑调度。被问"为什么迁 K8s"时，先证明你懂 YARN 的好（成熟稳定），再说 K8s 的增量（统一底座、GPU、生态）。

### Q26. Spark shuffle 的 Bypass 机制阈值？
`spark.shuffle.sort.bypassMergeThreshold`（默认 200）：**无 map 端聚合的普通 shuffle**，且分区数 ≤ 阈值时，走 BypassMergeSortShuffleWriter——每个分区直接开一个临时文件（不排序不缓存），最后合并——小作业省 CPU。超过阈值或需要 mapSideCombine → 排序路径。能讲出"为什么 mapSideCombine 就不能 bypass"（聚合要在排序流上做）就到源码层了。

### Q27. Spark 的数据本地化（locality）怎么调？
级别：PROCESS_LOCAL → NODE_LOCAL → RACK_LOCAL → ANY，等待超时后降级调度（`spark.locality.wait` 及分级参数）。**数据平台场景**：HDFS 数据本地化在 K8s 上天然弱化（Pod 不绑定数据节点）——这也是"计算仓储分离"架构的代价之一，用 Alluxio/缓存或直接接受网络 IO。

### Q28. ★ Flink Watermark 深入：乱序、迟到数据怎么办？
Watermark = 当前事件时间 - 允许乱序度，**到达即触发此前窗口计算**。迟到数据三档处理：① 窗口已关闭但未超 allowedLateness → 更新窗口结果（需要状态保留 + 下游可覆盖写）；② 超 allowedLateness → **侧输出流（side output）**单独落表，离线校准；③ 完全丢失 → 对账发现。**调参**：乱序度 = P99 事件时间延迟（监控出来），不是拍脑袋的 5 秒。

### Q29. Flink 双流 join 的状态膨胀怎么办？
Regular Join 状态无限增长（双方所有历史都留）→ 三招：① **Interval Join**（时间区间内的 join，状态自动过期——订单-支付 30 分钟窗口的标配）；② **Temporal Join**（维表版本 join，changelog 湖表）；③ 状态 TTL 兜底。**面试追问**：interval join 的数据乱序边界？（watermark 约束两侧区间，迟到数据进侧输出）。

### Q30. Kafka 分区分配策略与消费顺序保证？
分配策略：RangeAssignor（按主题逐个分配，易不均）→ **CooperativeStickyAssignor**（增量 rebalance 不断消费，1.1+ 推荐）。**顺序性**：Kafka 只保证分区内有序——需要全局有序就单分区（牺牲吞吐），业务级顺序靠"同一业务 key 路由同一分区"（producer 指定 key）。**追问**：rebalance 期间消息会丢吗？（不会，只暂停；配合 static membership 减少触发）。

### Q31. Hive 的 CBO 与向量化执行？
向量化（hive.vectorized.execution.enabled）：一次处理一批（1024 行）代替逐行，CPU cache 友好，ORC 读性能 3~10 倍；CBO（hive.cbo.enable + 统计信息 analyze table）基于 cardinality 选 join 顺序。**失效场景**：复杂 UDF/自定义 InputFormat 会让向量化退化回逐行——`explain` 里看 "Vectorization: false" 及原因。

### Q32. Spark 作业的 GC 调优怎么和内存配置联动？
链路：GC 日志分析（停顿分布）→ 常见根因（对象创建过多：缓存粒度太细、字符串重复；老年代碎片：CMS 时代）→ 动作：Kryo 序列化减对象体积、cache 用 MEMORY_AND_DISK、executor 堆 8G+ 换 G1（`-XX:+UseG1GC -XX:MaxGCPauseMillis=100`）、大对象 region 调整。**与 K8s 联动**：GC 停顿期心跳丢失会被 kubelet 判死——requests/limits 与 GC 行为要对齐（07 篇 Q8/Q9 的续篇）。

# 深挖补充（防问倒版）：机制细节与追问实录

## 深挖 1：Spark Sort Shuffle 的写入与读取全流程

**写端（ShuffleMapTask）每个 task 的流程**：
1. 每条记录经 `Partitioner`（默认 HashPartitioner，`key.hashCode % numPartitions`）算出目标分区；
2. 数据不立即落盘，先进 **PartitionedAppendOnlyMap / PartitionedPairBuffer**（执行内存里的哈希表/数组，按分区 id 排列）；
3. 内存达到阈值（`spark.shuffle.spill.initialMemoryThreshold` 起，每次增长 `spark.shuffle.spill.chunkSizeInBytes` 检查）→ 触发 **spill**：按分区 id（必要时按 key）排序，逐分区写出临时文件的一段；
4. 最终把内存剩余 + 所有 spill 文件 **merge 成一个数据文件 + 一个索引文件**（记录每个下游分区的 offset/length）——这就是"每个 task 一个数据文件"的由来；
5. MapStatus（本 task 各分区大小，超阈值用压缩位图 HighlyCompressedMapStatus）上报给 DAGScheduler/MapOutputTracker。

**特殊情况——Bypass 路径**（`bypassMergeThreshold=200`）：无 map 端聚合 + 分区数 ≤200 时，每条记录**直接开一个分区临时文件**（不排序不缓存，省 CPU），最后合并成同样结构。所以"分区数少时不排序反而更快"的原因在此。

**读端（ShuffleRDD 的 ReduceTask）**：通过 MapOutputTracker 拿到"我的分区在哪些上游文件的第几段"→ BlockStoreShuffleReader 远程拉取 → 若需要聚合（`aggregator.isDefined`）用 **ExternalAppendOnlyMap**（哈希表，满了 spill 成排序文件，最后归并聚合——和 MR 的 merge 思路同源）→ 输出。

**追问实录**：
- 问："map 端文件数到底怎么算？" 答：Sort Shuffle 下 = task 数 × 1（数据文件）+ task 数 × 1（索引）；对比 Hash Shuffle 的 task 数 × 下游分区数——这就是 2.0 移除 Hash Shuffle 的原因。
- 问："为什么 Sort Shuffle 大数据量时也不慢？" 答：Tungsten 序列化排序——数据以二进制形式在 off-heap 排序，不做 Java 对象反序列化，排序操作直接比较二进制指针（RadixSort 支持 string prefix）。
- 问："什么配置能让它退化？" 答：mapSideCombine=true 的聚合类算子 + 分区数超 bypass 阈值 → 必须走排序路径；以及 `spark.shuffle.compress` 关掉后 IO 翻倍。

## 深挖 2：数据倾斜——两阶段聚合的完整 SQL 与 AQE 参数表

**加盐两阶段（SQL 形态，Hive/Spark 通用）**：

```sql
-- 阶段一：key 拼上 0~9 的随机前缀，局部聚合
SELECT concat(key, '_', cast(floor(rand()*10) AS int)) AS salted_key,
       sum(cnt) AS partial_cnt
FROM detail GROUP BY concat(key, '_', cast(floor(rand()*10) AS int));

-- 阶段二：去掉前缀，全局聚合
SELECT split_part(salted_key,'_',1) AS key, sum(partial_cnt) AS cnt
FROM (阶段一结果) GROUP BY split_part(salted_key,'_',1);
```

**Join 倾斜的膨胀法（大表倾斜 key 处理）**：倾斜 key 单独拎出 → 大表该 key 的行复制 N 份（`explode(sequence(0,N-1))` 打标 0..N-1）→ 维表同样复制 N 份并打同样标 → 按 (key, 标) join → union 回主流程。代价：维表膨胀 N 倍，所以 N 只对倾斜 key 生效。

**AQE skewJoin 参数表**（3.0+ 自动拆倾斜分区）：

| 参数 | 默认 | 含义 |
|---|---|---|
| spark.sql.adaptive.skewJoin.enabled | true | 开关 |
| skewdInPartitionFactor | 5 | 分区大小超过"中位数×5"判定倾斜 |
| skewedPartitionThresholdInBytes | 256MB | 且超过该绝对大小才处理 |
| skewedPartitionFactor 与阈值同时满足才拆 | — | 双条件防误判 |

**追问实录**：
- 问："AQE 拆了倾斜分区为什么有时还慢？" 答：拆分后同一倾斜 key 仍要和维表同一段数据 join 多次，维表是广播的才有效；若维表也是大表（sort-merge join），拆分效果差——此时仍要膨胀法或改维表设计。
- 问："sum 和 count(distinct) 混在一起的两阶段怎么做？" 答：先 count(distinct) 单独两阶段（或 bitmap），sum 走普通聚合，最后 join 对齐——别在一个聚合里硬解决。
- 问："倾斜治好了但shuffle 读还慢？" 答：查下游网络/磁盘（K8s 上是 emptyDir 的磁盘 IO 配额）和 fetch 重试次数。

## 深挖 3：Flink credit-based 反压机制（1.5+ 默认）

**机制**：每个 InputChannel（对应上游一个 subtask）维护 credit（可用 buffer 数）。下游定期把 credit 告诉上游；上游发送数据时按 credit 发、不够就攒在 OutputQueue。**效果**：下游消费多快，上游就发多少——网络不再无限堆积（1.5 之前靠 TCP 反压，效果差且延迟大）。

**反压传导链（从下游到上游）**：Sink 写慢 → 算子输出 buffer 占满 → input credit=0 → 上游发送阻塞 → 上游算子输出积压 → 逐级往 source 传导 → source 停止从 Kafka 拉取 → 消费 lag 增长。

**排查组合拳**：
1. WebUI Backpressure 标签：busy/backPressured/idle 三个百分比（1.13+）；
2. 火焰图（开启 `rest.flamegraph.enabled=true`）看热点是用户函数还是序列化/网络栈；
3. Metrics：`outPoolUsage/inPoolUsage`、`numRecordsOutPerSecond` 与输出的衰减点定位到具体算子。

**追问实录**：
- 问："为什么反压会导致 checkpoint 失败？" 答：barrier 是跟在数据流后面排队的，反压时 barrier 在积压 buffer 里排队，对齐超时（默认 `checkpoint.timeout` 10min）→ 失败。unaligned checkpoint 让 barrier 插队并把被跨越的在途数据写进快照，专治反压期 checkpoint 失败（代价：快照变大、恢复更慢）。
- 问："反压定位到 sink 写 JDBC 慢，怎么改？" 答：批量写（batch size + rewrite）、连接数 = sink 并行度 × 每任务连接池上限、必要时 sink 端先按 key 预聚合减少写次数；还是不够就加 sink 并行度并接受数据倾斜检查。

## 深挖 4：RocksDB StateBackend 的内存构成——著名的容器 OOM 坑

RocksDB 是 **C++ 堆外**实现：它的写缓冲区（write buffer）、块缓存（block cache）、索引与 bloom filter 都占 **native memory**，不受 JVM -Xmx 管，但受容器 cgroup limit 管！

**Flink 的隔离机制**：`taskmanager.memory.managed.fraction`（默认 0.4）划出一块 managed memory 按比例分给 RocksDB——**理论上** RocksDB 只能用这块。但坑在：block cache/write buffer 的实际用量由 RocksDB 自己的选项控制（BlockBasedTableConfig），配置不当会**突破 managed 配额直接吃 native 内存** → 容器 cgroup OOMKilled，且 JVM 层面无任何日志（这是最迷惑的排障点——java 进程看着好好的，pod 就死了）。

**排查三板斧**：① 容器层看 OOM 事件（`kubectl describe pod` 的 Reason: OOMKilled + exit 137）；② Flink WebUI 的 Memory Configuration 页核对 managed 分配；③ RocksDB metrics（block cache usage / memtable usage）对齐 managed 配额。

**追问实录**：
- 问："state 从 HashMap 换 RocksDB 后 pod 频繁 137？" 答：九成是 total Flink 内存配置没变——RocksDB 的 native 用量从"堆内"变成了"堆外 managed"，而容器 limit 没给 managed 留足；重算 `taskmanager.memory.process.size` 全景（JVM heap + managed + network + metaspace + overhead）。
- 问："checkpoint 期间抖动？" 答：RocksDB checkpoint 时写 SST 到远端，与 compaction 抢磁盘 IO——本地盘配额与 checkpoint 间隔一起调。

## 深挖 5：Kafka HW/LEO 与 ISR 的动态维护

- **LEO**（Log End Offset）：每个副本的下一条待写 offset；**HW**（High Watermark）：min(所有 ISR 副本 LEO)，**消费者只能读到 HW 之前**。
- **流程**：producer 写 leader → follower pull → leader 更新本地 LEO 与远程 LEO 视图 → HW = min(ISR LEO) → follower 的 HW 在下一轮 fetch 响应里被动更新（**这里有个历史坑：HW 更新滞后一轮，0.11 后 leader 统一管理 HW**）。
- **ISR 收缩**：follower 落后超过 `replica.lag.time.max.ms`（默认 30s）→ leader 踢出 ISR（写进 zk/控制器）；**扩张**：追上后自动加回。**unclean 选举**：ISR 全挂时是否允许非 ISR 副本当 leader——`unclean.leader.election.enable=false` 时宁可分区不可用也不丢数据（C/A 取舍的活例子）。
- **追问实录**："acks=all 但还是丢了一条？" 排查：① min.insync.replicas 是否配了（没配时 all 等价于 1）；② 是否开过 unclean 选举；③ producer 幂等是否开（重试导致的乱序重复也是"丢语义"的近亲）。
