# 04 — 湖仓一体与实时数仓 18 题（2025–2026 增量考点）

> 这是当前企业面试**增速最快**的考区。背景：传统 Hive 离线数仓的 T+1 时效、HDFS 存储成本、Lambda 架构双链路一致性，正被 "Flink + 湖格式（Paimon/Hudi/Iceberg）+ OLAP（Doris/StarRocks/ClickHouse）" 的实时湖仓组合替换。面试官通过这组题判断你"是否在技术演进的浪头上"。标 ★ 必问。

## A. 湖格式三巨头（7 题）

### Q1. ★ Paimon / Hudi / Iceberg 怎么选？三者定位差异？

【参考回答】一句话定位：**Iceberg** 是"表格式标准派"（中立、引擎兼容性最广、适合 Spark/Trino 主导的存量体系）；**Hudi** 是"更新派"（COW/MOR 双模型、upsert/增量查询成熟、CDC 场景积累深，但 Compaction 调优复杂）；**Paimon** 是"流式湖仓派"（Flink 原生、LSM 结构天然支持高吞吐流式写入与更新、partial-update/aggregate 合并引擎内置）。**选型方法论**：主计算引擎是什么（Flink 生态 → Paimon 亲和；Spark/Trino 存量 → Iceberg）；更新负载占比（高频 upsert → Paimon/Hudi；纯追加 → Iceberg 足够）；团队运维能力。我们选 Paimon 的三条理由 + 放弃 Hudi 的两条代价（见 03 篇 Q24），是标准答法。

【追问链】Paimon 主键表和 Append 表的区别？（主键表：LSM，支持 upsert/部分更新，查询需 merge-on-read；Append 表：纯追加，写入快、查询需后台 compaction 合并小文件）→ 为什么说 Paimon 解决了"对象存储高频更新的 IO 放大"？（传统做法按文件重写，Paimon 用 LSM 把更新先落有序小文件 + 后台 compaction，随机写变顺序写）

### Q2. ★ Paimon 的 LSM 结构与 Snapshot 机制？（源码级问题）

【参考回答】主键表按 key 分桶，桶内是 **LSM 树**：MemTable → 有序文件（SST），levels 层级 compaction。读取时 merge-on-read：内存表 + 各层 SST 按 key 归并（结合 merge engine：deduplicate/partial-update/aggregate/first-row）。**Snapshot**：每次提交生成一个不可变快照（指向当前 manifest 列表），**Time Travel**（查历史版本）、**增量读取**（读两个 snapshot 之间的变化——下游流式消费的基石）都靠它；过期快照由 expire 机制清理（对应"回溯期"配置）。**面试加分**：讲 compaction 的两种触发（写入时同步/后台异步）与 write-buffer 调优。

【追问链】Time Travel 有什么实际用途？（错误数据回滚到旧版本、审计、模型训练取特征快照——数据一致性）→ Snapshot 积压会怎样？（元数据膨胀 + 对象存储 list 变慢，必须配 expire）

### Q3. 湖表和 Hive 表到底差在哪？（本质题）

【参考回答】四点：① **ACID 提交**——湖表用快照原子提交，Hive 表并发写靠 rename 目录"最后一写赢"（互踩）；② **增量读取**——湖表天然支持流式消费变化，Hive 只能全量扫或用额外标记表模拟；③ **更新/删除**——湖表主键表原生支持，Hive 靠全表重写或 ACID 事务表（运维重）；④ **schema evolution**——湖表安全加列/改注释且历史数据兼容，Hive 加列靠 metadata-only（有数据对不齐的经典坑）。**一句话：Hive 表是"文件 + 目录约定"，湖表是"带事务日志的真表"。**

### Q4. 什么是 merge-on-read（MOR）和 copy-on-write（COW）？怎么选？

【参考回答】COW：更新时重写整个数据文件——读快（无需归并）、写放大高，适合读多写少；MOR：更新只写增量文件（delta），读时归并——写快、读有 merge 开销，靠 compaction 周期性归并控制读放大。**实践**：实时入湖（Flink 高频写）必然 MOR + 后台 compaction；离线每天批量更新的维度走 COW 或干脆 Hive。追问预警：MOR 的"读放大"怎么观测？（查询时 merge 的文件数、compaction 积压量）。

### Q5. 小文件问题在湖上有什么不同？

【参考回答】湖格式本身有 manifest/index 缓解 planner 压力，但**数据文件本身**仍会小：Flink 每次 checkpoint 提交生成一批新文件（默认几十秒一次 × 并行度）。治理：① checkpoint 间隔拉长（1~5min，用时效换文件数）；② Paimon 的 write-buffer + compaction 合并；③ Iceberg 的 rewrite_data_files 定时任务；④ 分区粒度别太细（小时级分区比 10 分钟级文件少 6 倍）。**量化表述**：某核心表从日均 5w 文件治理到 2k。

### Q6. 湖表的 schema evolution？生产怎么用？

【参考回答】加列（任意位置）、改注释、列重命名（Iceberg/Paimon 支持，基于列 ID 而非名字）都是安全操作；**删列和改类型是危险操作**（涉及重写数据）。生产流程：上游 CDC 字段新增 → Flink CDC 自动同步（schema evolution 开启）→ 湖表自动加列 → 下游 SQL 引用新列。**加分**：讲一个"上游悄悄改字段类型，湖表写入报错被 schema 校验拦住"的案例——没有湖表时这种变更静默污染下游数月。

### Q7. 湖上的 Time Travel + 增量读，你们实际用在什么场景？

【参考回答】三个真实用法：① **事故回滚**：错误作业写坏表 → rollback 到出错前 snapshot，分钟级恢复（对比 Hive 时代的"从 ODS 重算 3 天"）；② **下游增量消费**：DWS 汇总任务改成读上游两个 snapshot 之间的增量（替代"扫描昨天分区"）；③ **特征回填**：训练特征要求"当时视角"，time travel 直接取历史版本。**代价提示**：回溯期 = 存储成本，配 expire 策略（核心表 7 天，普通表 1 天）。

## B. 实时数仓架构（6 题）

### Q8. ★ 你理想中的实时数仓分层架构？

【参考回答】（画架构的题，按层说）**ODS**：Flink CDC 从业务库直捕 binlog + 业务日志进 Kafka，写入 Paimon ODS 表（保留原始语义）；**DWD**：Flink 流式清洗/维度展开（维表关联用广播 state 或 temporal join 湖表），写 DWD 湖表——**实时明细可回溯是和"纯 Kafka 链路"最大的差别**；**DWS**：Flink 聚合或 StarRocks 物化视图，分钟级更新；**ADS**：StarRocks/Doris 直接服务看板与接口（秒级 OLAP）。**一致性**：离线链路保留，做"每日校准"（实时结果 vs 离线结果对账，diff 告警）——**没有对账的实时数仓不敢对外承诺口径**。

【追问链】为什么不全走实时？（实时不可回刷——上游重导历史，实时链路无法重放几天前的窗口；离线兜底是正确性下界）→ Kafka +ClickHouse 的老方案为什么不推荐了？（明细不可查、不可回溯、多层 join 弱——湖表解决了这些）

【动手印证】llmops-labs Lab 06 的架构注释即"迷你版"（模型服务为类比）；k8s-labs Lab 10 是计算层。

### Q9. 流批一体到底"一体"在哪？代价是什么？

【参考回答】**三层次**：① 计算引擎一体（Flink 同一套 SQL 跑批和流）；② 存储一体（湖表同时服务批读与流读——Paimon 增量读是关键）；③ **建模一体**（同一套分层模型，实时写 DWD/DWS，离线只做校准——消灭 Lambda 双链路的口径分裂）。**代价必须讲**：Flink 批模式性能仍弱于 Spark（大回刷场景常降级回 Spark 读湖表）；一套代码同时满足 exactly-once 与批量高吞吐，调优要两头照顾；团队需要同时懂流和批的工程师。

【追问链】回刷大历史数据怎么办？（Flink 批模式跑湖表，或 Spark 读 Paimon 写湖表——引擎可换，存储不动）

### Q10. Lambda 和 Kappa 架构的区别？你们在哪一层？

【参考回答】Lambda：实时+离线双链路，各自建模，最后结果合并——一致性地狱但稳；Kappa：一切皆流，需要历史就重放 Kafka（前提：Kafka 保留期够长 + 幂等重算）。**现在的主流答案**："Lambda 简化版"（实时为主 + 离线校准）或"湖仓 Kappa+"（湖表既当流又当批的存储，重放湖表而不是 Kafka）。**表态**：我们实时看板走 Kappa+，财务类强一致场景保留离线为准。

### Q11. 实时指标和离线指标对不上，怎么排查？

【参考回答】经典五因：① **时间语义**（事件时间 vs 处理时间，watermark 延迟）；② **口径差异**（实时漏了去重逻辑/维表版本）；③ **乱序迟到**（离线全量 vs 实时窗口关闭）；④ **上游重放**（离线修正了历史，实时没同步）；⑤ **写入时点**（快照时刻不同）。**治理**：对账任务逐层 diff（ODS 对 ODS、DWS 对 DWS）定位到层；允许 N% 内的"迟到差异"，超阈值告警。**加分**：说"我们把'实时数允许的误差模型'写进了指标平台文档"。

### Q12. Flink 作业的状态越跑越大，你们怎么治理？

【参考回答】治理清单：**TTL**（所有去重/维表缓存 state 必设，先灰度后全量）；**状态结构**（大 Map 拆细、对象序列化用 Kryo→Pojo 调优）；**RocksDB 增量 checkpoint**（对比全量：XL 状态下 checkpoint 从 40min 到 3min）；**闲状态下线**（指标迁移后旧 state 清理要显式）。**数字**：状态从 40TB → 8TB，checkpoint 失败率从周均 3 次到 0。

### Q13. Exactly-once 端到端在你们的链路里怎么保证？（跨引擎题）

【参考回答】分段保证 + 边界补偿：Kafka→Flink（checkpoint 记 offset）→ Flink→Paimon（湖表提交原子性，checkpoint 对齐 commit）→ Paimon→StarRocks（定时/增量同步，幂等主键表）。**外部系统**（如短信）天然 at-least-once → 业务幂等（去重表）。**金句**：端到端 exactly-once 是"分段事务 + 边界幂等"的组合，没有银弹。

## C. OLAP 引擎（3 题）

### Q14. Doris/StarRocks 的架构原理？为什么快？

【参考回答】FE（元数据/查询规划，多副本）+ BE（数据存储与计算，MPP）。快的原因：**列存 + 向量化执行**（batch 处理替代逐行，CPU cache 友好）、**前缀索引 + 分区分桶裁剪**、**MPP 并行**、**物化视图/Rollup 预聚合**。数据模型：Duplicate/Aggregate/Unique（主键）—— Unique 模型支持部分列更新（用户画像宽表常用）。**K8s 视角**：BE 是有状态重资源（本地盘友好），混部要专池。

【追问链】分区分桶怎么设计？（分区=时间，桶=高频查询 key 的 hash，单桶 1~10GB 经验值）→ Unique 模型的 merge 时机？（写入时/查询时 merge， Compaction 策略）

### Q15. ClickHouse 和 Doris/StarRocks 怎么选？

【参考回答】**ClickHouse**：单表极限性能之王（列存+向量化极致），适合日志分析、宽表点查、超大规模；**短板**：多表 join 弱（要宽表化/字典）、并发能力一般、运维（zookeeper 依赖、版本碎片）。**Doris/StarRocks**：join 强、SQL 兼容好、并发高，适合"直接查明细+多表关联"的数仓加速场景。**选型口诀**：单表超宽、亿级点查、日志 → CK；多表 join、即席分析、湖上查询 → Doris/StarRocks。我们两者并存：日志平台 CK，报表加速 Doris。

### Q16. 物化视图/预聚合的一致性怎么管理？

【参考回答】三态：**同步物化**（写入时同步更新，强一致、写入放大）、**异步刷新**（定时/事件驱动，最终一致——要暴露"数据时点"给业务）、**查询时聚合**（无预聚合，实时但慢）。实践：核心财务指标同步或分钟级异步 + 基线校验；运营看板异步 + 页面标注"更新时间"。

## D. 成本与治理（2 题）

### Q17. 存算分离你们怎么做的？收益和坑？

【参考回答】湖格式天然存算分离（数据对象存储 + 计算容器任意调度）：**收益**——计算按需伸缩（大促扩 executor、闲时缩容）、存储无限且便宜、多集群共享同一份数据；**坑**——对象存储延迟与 list 性能（元数据缓存/manifest 优化）、本地缓存层（Alluxio/StarRocks file cache）几乎必配、小文件在对象存储上被放大。**数字**：存储成本降 60%（HDFS 三副本 → EC/对象存储），计算利用率升 20 个点。

### Q18. 整库 CDC 入湖的架构与坑？

【参考回答】Flink CDC Pipeline：MySQL binlog → 整库同步到 Paimon（自动建表 + schema evolution），下游按表建 DWD。**坑清单**：① 全量+增量切换瞬间的断流（CDC 框架的 snapshot→binlog 衔接，监控 delay 指标）；② **schema 变更**（加列自动、类型变更要停管道人工处理）；③ 大表全量阶段的反压与断点续传；④ 无主键表的选择（Append 表 + 去重逻辑下沉）。**收益**：新业务域入仓从"周级开发"到"天级配置"。

## E. 进阶追问库（6 题）

### Q19. Iceberg v2 的 delete file 是什么？
v2 引入行级删除：**position delete**（记录"文件 X 第 N 行删了"，读写快但 compaction 要合并）与 **equality delete**（"key=Y 的删掉"，写入方便但读放大）。读到旧数据文件 + 应用 delete file = 当前视图。**与 Paimon 对比**：Paimon 用 LSM（DelteRecord 在 SST 层级归并），思路不同目标一致——能对比讲清两者，说明读过底层。

### Q20. Paimon 的 compaction 策略与 changelog 产生？
写入触发（同步，影响吞吐）与后台异步（专用 compaction 作业）两条路；`full-compaction` 模式下每次全量压缩并**产生完整 changelog**（下游可流式消费变化——这是 Paimon 对比 Iceberg 的流式优势）。**调优**：小文件与读放大之间平衡，写密集表用异步 + 分区级并行 compaction。

### Q21. 湖表的乐观并发控制：冲突了怎么办？
湖表提交 = CAS 快照引用（基于旧 snapshot 提交新 snapshot）；两个作业同时提交 → 后者失败重试。**Flink 写入靠分桶规避冲突**（同一 key 固定到同一 writer，不同作业写同一表仍需规划）；Hive 表跨引擎并发写要靠 lock（Hive metastore 锁或外部锁）。**设计原则**：一张表的实时写入者唯一，离线回刷错开窗口。

### Q22. StarRocks 的查询优化器与 Colocate Join？
CBO 基于统计信息（行数/NDV）选 join 顺序与分发方式；**Colocate Join**：两表按相同分桶键分布，数据本地 join 免网络 shuffle——大表 join 提速 3~10 倍的关键，建表时用 `COLOCATE WITH` 声明同分布组。**面试点**：为什么"分桶键=高频 join 键"是 Doris/StarRocks 建模的第一原则。

### Q23. ClickHouse 的 ReplicatedMergeTree 与分布式表？
本地表（ReplicatedMergeTree，靠 ZooKeeper/KeepAlive 做副本协调）+ 分布式表（逻辑视图，按分片键分发查询）。**坑**：分布式表 join 是"逐分片拉取"（低效），标准做法各分片先本地聚合再汇总（两层查询/物化视图）。和 Doris 的"一体式 MPP"对比是高频追问。

### Q24. 湖上的权限怎么做？
三层：**存储层**（对象存储/HDFS 权限是底线）、**表层**（湖格式本身的 RBAC：Iceberg/Paimon 集成 Ranger/Doris 权限）、**查询层**（Trino/StarRocks 的 catalog 级权限）。**数据分级联动**（呼应 02 篇 Q25）：L4 列级脱敏在查询层做 masking policy。**现实**：很多公司湖权限是"裸奔"的——能讲出三层模型就超过 90% 候选人。

# 深挖补充（防问倒版）

## 深挖 1：Paimon 主键表的 LSM 分层与 compaction 细节

**结构**：主键表按 `bucket` 分片（`bucket-key` hash，默认 -1 为动态分桶）；每个桶内是 LSM：**MemTable（内存）→ 最新 SST 层 → 更老 SST 层**，每层是若干 "sorted run"（内部有序的文件集合，层间 key 范围可重叠）。**读**：所有 sorted run 归并（merge-on-read，按 merge engine 处理：deduplicate 取最新 / partial-update 非空覆盖 / aggregate 预聚合 / first-row 保留首见）。

**compaction 策略**（表属性 `compaction.optimization-interval`、`write-buffer` 等控制）：
- **universal compaction**：把大小相近的 sorted run 合并，控制读放大（默认思路，类 RocksDB）；
- **full compaction**：把桶内所有 run 合成一个——最彻底但最贵，**产生完整 changelog**（下游流式消费变化的前提）；
- **写入时同步 compaction** vs **独立 compaction 作业**（`compact` action 定时跑）——写密集表选后者，接受读放大窗口。

**追问实录**：
- 问："读放大怎么观测？" 答：查询 profile 的"扫描文件数/merge 的文件数"；或 `SELECT * FROM table$options` 与 system 表看每桶文件数——超过几十个 sorted run 必须压。
- 问："changelog 模式的代价？" 答：只有 full-compaction 能产生完整 changelog，意味着 compaction 频率提高 → 写放大；下游不消费变化就别开 changelog.producer=full-compaction，用 lookup 或 none 省 IO。

## 深挖 2：Flink 写 Paimon 的一致性对齐

Flink checkpoint 与 Paimon commit **对齐**：checkpoint 完成时才 commit 一个 snapshot（两阶段：预写文件 → 提交快照）。**这就是湖表天然 exactly-once 的来源**——失败重放的数据在未提交 snapshot 里，不生效。**参数要点**：`sink.checkpoint-interval`（写入延迟 = 该值，大促可调小但小文件增多）；`write-buffer-size`（太大 OOM、太小小文件）；`commit.force-compact`。

**追问实录**："下游多久能看到数据？" 答：Flink 写入侧 = checkpoint 间隔；若走 StarRocks 外表查询 = 即时（读湖最新 snapshot）；若离线同步 = 同步任务周期。把"数据可见延迟 = min(写入间隔，同步周期)"讲清是资深信号。

## 深挖 3：StarRocks 查询湖表 vs 内表的性能差与决策

外表查询（External Catalog 直读 Paimon/Iceberg）：**省 ETL、时效好**，但扫 parquet/orc 无本地索引缓存，比内表慢 3~5 倍（首次无 cache 更慢）。**实践分层**：高频报表 → 内表（Routine Load/Broker Load 导入 + 物化视图）；低频即席分析、长尾探索 → 湖外表（配 file cache：`datacache.enable=true`）。**追问**："物化视图和导数到内表什么区别？" 答：物化视图是"查询时透明改写"，导数是"显式 ETL"——前者运维轻但受改写能力限制，后者可控但要管理依赖。

## 深挖 4：湖表 ACID 的并发冲突细则（Paimon 为例）

**冲突场景**：两个 Flink 作业写同一张主键表 → commit 时基于的 snapshot 已被对方推进 → 冲突失败。**规避设计**：① 主键表按 bucket 分——两作业写同一表不同 bucket 键 = 不可能（bucket 是表属性）→ **正确姿势是一张表只有一个实时写入者**；② 追加表冲突少（不同文件不重叠，可配置 allow）；③ Schema 变更与写入冲突 → 序列化处理。**回刷**：实时写入暂停窗口 或 离线引擎写不同表后 swap。
