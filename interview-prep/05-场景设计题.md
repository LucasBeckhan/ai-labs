# 05 — 场景设计题 6 大场景（二面主战场）

> 场景题没有标准答案，面试官考的是**思考框架**：先澄清需求与规模 → 列约束 → 分层拆解 → 给出取舍 → 主动暴露风险。以下每个场景都按这个骨架给出"高分答题路径"。回答时永远先问澄清问题（数据量？时效？预算？团队？）——**不问就答 = 减分**。

## 场景一：从 0 搭建一个实时数仓（业务：电商大屏 + 用户画像）

**澄清问题**：数据源有哪些（MySQL binlog/埋点日志）？日增量多少？看板要求秒级还是分钟级？需要回溯多久？

**高分答题路径**：
1. **分链路**：binlog → Flink CDC → Paimon ODS；埋点 → Kafka → Flink 清洗 → Paimon DWD；
2. **分层建模**：DWD 明细（实时可查可回溯）、DWS 用 Flink 聚合 + StarRocks 物化视图双写（大屏走物化视图秒级，画像标签走 Flink 维表 join 写 HBase/StarRocks）；
3. **正确性**：保留离线链路做每日校准对账，diff 告警（0.1% 阈值）；
4. **运维**：checkpoint 调优（间隔/unaligned）、反压告警、K8s 上 Flink 作业双活；
5. **演进路线**：先大屏（3 周）→ 画像（2 月）→ 全域分层（半年），**不要一上来全覆盖**。

**面试官在听的点**：对账机制（没提直接降档）、回溯能力（湖表 vs 纯 Kafka 的理由）、演进节奏（证明落地过）。

**结合实验**：llmops-labs Lab 06 的实时服务架构 + k8s-labs Lab 10 的计算容器化。

## 场景二：千亿级数据的精确去重（UV 类指标）

**澄清问题**：精度要求（精确还是 1% 误差可接受）？查询模式（按天/按月/任意时段）？QPS 多少？

**高分答题路径**（按精度递进）：
1. **估算可行**：`count(distinct)` 在千亿级直接跑 = shuffle 风暴 → 先说"不精确方案"：HyperLogLog（误差 ~1%，占存 1.5KB/key 组，Doris/CK 原生）；
2. **精确方案 A**：两阶段去重（先按用户×天聚合，再跨天聚合）——把 O(千亿) 的 shuffle 变成 O(亿级)；
3. **精确方案 B**：**bitmap**——用户 id 映射成整数（维表 id-mapping），按分区存 RoaringBitmap，任意时空调集（CK/Doris 原生函数，Paimon 聚合表 `bitmap` merge engine）；亿级用户 bitmap 单日 ~10MB 级；
4. ** id-mapping 的代价**：新用户注册要同步分配整数 id，离线场景用延迟 T+1 分配。

**面试官在听的点**：先问精度再开药（顺序对了就加分）；bitmap 的 id 分配方案；"精确去重是要花代价的"这个认知。

**结合实验**：llmops-labs 知识库与 Lab 04 评估思想同源——"先澄清指标定义再实现"。

## 场景三：指标口径全面治理（指标平台建设）

**澄清问题**：现有报表数量？口径冲突的严重程度？有没有元数据基础？

**高分答题路径**：
1. **盘点**：爬取所有报表 SQL，解析聚合函数+过滤条件+来源表，聚类出"同名不同义/同义不同名"清单（给数字：43 个活跃口径）；
2. **建模**：原子指标（不可再分，如支付金额）+ 修饰词（终端/渠道）+ 时间周期 → 派生指标命名规范 `sum_payment_1d_pc`；
3. **落地**：公共口径全部沉到 DWS 一张物理表，指标平台只存"定义 → 物理字段"映射；报表接平台 API 取数；
4. **机制**：口径变更审批 + 血缘影响面自动通知 + 新指标强制从平台创建；
5. **效果量化**：口径收敛 43→6、对账工单月均 20+ → 2、新报表开发从 3 天到 0.5 天。

**面试官在听的点**：有没有"机制"（不是一次性运动）；业务方抵制怎么处理（保留自定义口径但打标签）。

## 场景四：历史数据规则变更，需要回刷 3 年数据

**澄清问题**：涉及多少表/分区？下游依赖多深？有没有实时链路？回刷时间窗口？

**高分答题路径**：
1. **影响面**：血缘从变更表向下展开，圈出全部下游 + 各表的分区范围；
2. **正确性方案**：新旧双跑 diff 关键指标（先刷 1 天样本验证 diff=0，再全量）；
3. **执行设计**：按 DAG 拓扑逐层刷 + 就绪标记；专用回刷队列不抢日常 SLA；失败自动重试 + 断点续刷（分区级幂等 insert overwrite）；
4. **实时链路**：跨天回刷时实时任务暂停写入或引入修正流（对历史分区直接 overwrite 湖表）；
5. **预案**：保留旧分区快照（湖表 time travel 或备份表），diff 不达标一键回退；
6. **复盘机制**：回刷完成后把变更规则沉淀进"口径变更影响面"文档。

**面试官在听的点**：幂等（没提 overwrite/断点 = 危险人物）、双跑 diff、实时链路的处理（很多人会漏）。

## 场景五：大促保障（数据侧）

**澄清问题**：流量预估增长多少倍？哪些指标必须秒级？SLA 承诺是什么？

**高分答题路径**：
1. **分级**：核心链路（大屏 GMV/订单量，秒级）→ 重要（漏斗，分钟级）→ 一般（明细查询，可延迟）；
2. **资源**：实时作业提前扩容（K8s 拉起副本 / Flink 增并行度）、OLAP 副本扩容、**限流预案**（非核心查询降级）；
3. **预案演练**：故障注入演练（杀 executor/断上游/网络抖动）——演练过的预案才叫预案；
4. **基线管理**：离线侧核心任务最晚就绪时间按小时设卡，超时即告警到人；
5. **数据侧特有**：实时指标"预口径"和事后"精口径"双版本（大促当场给预口径，T+2 出精确数并声明差异）；
6. **复盘**：大促后出容量报告（实际 QPS/资源峰值/浪费点）反哺下次。

**面试官在听的点**：分级思想、演练过、预口径 vs 精口径的双版本设计（这是真实大促的标配，没听过说明没真保过）。

**结合实验**：k8s-labs Lab 09（HPA 弹性）、Lab 05（资源配额与驱逐）。

## 场景六：数据成本治理（三面加分题）

**澄清问题**：当前月成本构成（存储/计算/网络）？有没有作业级账单？

**高分答题路径**：
1. **建账单**：作业级"资源 × 时长 × 单价"，存储按"表 × 冷热分层"；没有账单先建账单；
2. **找出浪费 TopN**：无人访问的表（血缘 + 访问审计，90 天零访问）、重复计算（同一口径多任务跑）、资源配置虚高（CPU 利用率 < 20% 的任务）、小文件与冗余分区；
3. **治理动作**：下线/合并/降配/改存储格式（ORC→Parquet+ZSTD 或转对象存储 EC）、Spot/混部跑可重试任务；
4. **防回潮**：新任务上线强制走平台模板（默认合理资源）、月度成本红黑榜；
5. **量化**：月成本降 28%（利用率 35%→62%）——**先有度量再有治理**。

**面试官在听的点**：账单先行；技术动作与组织动作（红黑榜）并行——只讲技术的候选人在这个题上是"执行者"，讲了机制的才是"负责人"。

## 场景题答题通用心法

1. **先澄清后作答**：数据量、时效、精度、预算、团队——问 2~3 个再开始；
2. **分层拆解**：任何大问题都能拆成"采集→存储→计算→服务→治理"五段；
3. **主动暴露代价**："这个方案的坑是 X，我们用 Y 兜底"——40k 档面试官最想听的话；
4. **量化收尾**：每个方案都试着给出前后对比数字；
5. **不知为不知**：真没做过就说"这个规模我没实操过，但我会用 XX 方法验证"——编造会死得更惨。

## 场景七：元数据与血缘平台从 0 建设

**澄清问题**：组件清单（Hive/K8s 作业/BI 工具）？团队规模？有没有历史包袱（脚本散落各处）？

**答题路径**：
1. **采集优先**：任务级血缘从调度系统解析（DAG 依赖）、SQL 级血缘用 parser（自研或 DataHub ingestion）、BI 报表血缘从 BI 工具 API 拉——**全部自动化，不做人工登记**；
2. **模型**：实体（表/列/作业/看板/人）+ 关系（读/写/派生）图模型，DataHub/OpenMetadata 开箱或自研图库（Neo4j）；
3. **场景驱动**：先做"影响分析"（改表前查下游）和"下线治理"（无访问表回收）两个最高价值场景，别贪全；
4. **运营**：血缘覆盖率进数据团队 OKR，新任务接入 CI 强制登记。

**面试官在听的点**：先讲场景价值再讲技术（90% 候选人反着来）；覆盖率数字（如任务级 100%、字段级 70%）。

## 场景八：数据团队没有规范，新人来了各写各的，怎么建 DataOps？

**答题路径**：
1. **规范最小集**（先立 5 条能执行的，别写 50 条没人看的）：分层边界、命名规范、幂等要求、质量规则最低配、代码 review 必须；
2. **工具化执行**：规范进 CI（SQL linter / 命名检查 / 血缘自动登记）——靠人执行必死；
3. **模板化**：入湖/DWD/ADS 作业模板（配置驱动），新人 1 天出第一个合规任务；
4. **文化**：规范是"让新人更快"的工具而非约束——用"接入时间从 3 天到 0.5 天"证明价值；
5. **演进**：每季度回顾规范，删掉执行不了的，留下真实生效的。

## 面试官评分标尺（所有场景题通用）

| 档位 | 表现 |
|---|---|
| 不通过 | 直接给方案不澄清；只讲技术不讲代价；没有任何数字 |
| 勉强 | 澄清了需求，方案成立但单薄，追问两层开始含糊 |
| 通过 | 分层拆解清晰，主动暴露风险与代价，有粗略量化 |
| 加分 | 有"演进路线"（分阶段落地）+ 组织机制（不只是技术）+ 真实案例对照 |
| 强加分 | 反问出面试官隐藏的约束（如"现有实时链路要不要兼容"），并基于约束调整方案——把你当成未来的同事在讨论 |

# 追问实录：场景一（实时数仓）的完整模拟对话

> 这是一段模拟面试官与候选人的真实对话（追问到第 5 层）。自己练的时候照这个深度预演。

**面试官**：搭一个实时数仓，数据源 MySQL 和埋点，要求大屏秒级。你说说方案。

**候选人**：先确认两个问题：① 日增数据量和峰值 QPS？② 大屏指标是固定几个还是要灵活自助分析？假设日增 50GB、峰值 5w QPS、指标固定 20 个——方案：MySQL 走 Flink CDC 入 Paimon ODS，埋点进 Kafka 再 Flink 清洗入 DWD 湖表；固定指标用 Flink 聚合写 StarRocks 服务大屏；同时保留离线链路每日对账。

**面试官**：为什么大屏不直接查湖表，要写 StarRocks？

**候选人**：湖表是 merge-on-read，秒级查询的并发和延迟扛不住大屏 5s 刷新 × 多人查看；StarRocks 内表 + 物化视图是预聚合形态，查询是毫秒级。代价是多一条导数链路要维护一致性——用"湖表为准、StarRocks 为缓存副本"的定位管理。

**面试官**：Flink 聚合任务挂了怎么办？大屏会怎么样？

**候选人**：从最近 checkpoint 恢复（默认 1 分钟间隔），恢复期间大屏数据停更但不回退（StarRocks 里上次写入的还在）；恢复后先重放 checkpoint 之后的数据再继续。**这里有个细节**：恢复瞬间可能有几秒数据乱序写入，StarRocks 的 Unique 模型按主键覆盖能兜住，Duplicate 模型就会重复——所以聚合结果表用 Unique 主键模型。

**面试官**：MySQL 那边业务凌晨跑了历史数据订正，binlog 里涌出几百万条 update，你的链路会怎样？

**候选人**：Flink CDC 会把它们当成正常变更流式处理，下游 Join 维表、聚合都会跟着变——问题是时效（几百万条要消化几小时）和大状态（如果做了 join）。两个选择：① 限流消费让链路慢慢消化，接受大屏延迟几小时；② 识别出这是"历史订正"（比如业务方提前告知），走离线回刷通道直接改湖表分区，实时任务跳过这批（按业务标记过滤）。**关键是提前和业务方建立"历史订正要报备"的流程**——技术方案再好也架不住不报备的订正。

**面试官**：你说保留离线链路对账，对账的具体做法？

**候选人**：每日 T+1 对三个粒度：ODS 行数对 ODS（CDC 完整性）、DWS 指标对离线 DWS（口径一致性）、大屏快照对离线结果（最终呈现）。差异超过 0.1% 告警定位——常见差异源是事件时间乱序的迟到数据，处理方式是"实时数允许 N 小时内的迟到差异"写进口径文档。

**面试官**：这套链路你最担心什么？

**候选人**：诚实说两个：① Paimon 表的小文件和 compaction 在大促写入高峰的稳定性——需要提前压测并准备手动 compaction 预案；② 团队对湖表排障经验不足——我把排障 SOP 写进 runbook 并做过演练。**技术方案我有信心，人的因素要靠流程补。**

> 评分点：每个追问都落到具体机制（Unique 模型/主键覆盖/checkpoint 间隔），并且最后主动暴露"人的风险"——这就是 40k 档的回答质感。
