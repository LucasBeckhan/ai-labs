# 02 — 数据仓库 25 题（数仓建模 · 维度设计 · 指标 · 质量）

> 40k–50k 档的数仓面，考的不是"背分层"，而是**"这个业务域你有没有从头到尾负责过"**。每题按【面试官为什么问】【参考回答】【追问链】组织，标 ★ 的是我作为面试官的必问题。

## A. 分层架构（必问，6 题）

### Q1. ★ 数仓为什么要分层？每层做什么？

【面试官为什么问】一面第一题的常客。答"清晰好管理"这种话直接降档——分层是**工程决策**，每一层都有明确的职责边界和代价。

【参考回答】标准四层：
- **ODS** 原始层：贴源存储，不做清洗只做格式规整，保留全量/增量历史——**价值是"后悔药"**，任何下游错误都能从这里重算；
- **DWD** 明细层：清洗（去重/补全/脱敏）+ 维度退化 + 一事实一表，**粒度=业务过程最小粒度**（如一笔订单一行）；
- **DWS** 汇总层：按主题做轻度聚合（天/人粒度的指标中间表），**为了复用**——下游 10 个报表都要"用户+天"粒度，就沉一层避免重复算；
- **ADS** 应用层：直接对齐报表/接口的最终形态。
**分层的真实收益是三个"可"**：可复用（减少重复计算）、可追溯（血缘清晰，问题能定位到层）、可替换（任何一层重构不影响源和最终应用）。**代价也要讲**：链路变长 → 时延叠加、存储翻倍、任务依赖复杂——所以小规模场景可以压成两层，别为了分层而分层。

【追问链】
1. 每层的数据量量级？你们 ODS 多大、保留多久？（必答题：给数字，如 ODS 全量 XX TB 保留 90 天、增量按天 XX GB）
2. 轻度汇总层的粒度怎么定的？（看下游复用度：≥3 个下游用同一粒度才沉淀）
3. 分层任务依赖怎么管理？（调度系统 DAG + 就绪标记；讲你们用什么：DolphinScheduler/Airflow/内部平台）

【动手印证】本目录 `lab-数仓小实验/`——在真实 MySQL 里把 ODS→DWD→DWS→ADS 落一遍，跑通留存指标。

### Q2. 分层的好处你们实际感受到了吗？举一个例子。

【面试官为什么问】验证 Q1 是"背的"还是"用过的"。

【参考回答】给一个**返工故事**：某口径变更（如"活跃"定义从"打开 App"改为"产生任意事件"），因为中间层沉淀了"用户×天"活跃明细，只需要重刷 DWS 往下 3 张表；没有分层时 40 个报表各自算，改 40 处还容易漏。再补一个反面：早期 ADS 直连 ODS 的报表，口径改一次人工核对了三天——这就是后来推分层的原因。

### Q3. 数仓建设的方法论你了解哪些？OneData 是什么？

【参考回答】两大流派：**Kimball 维度建模**（总线矩阵、一致性维度、以业务过程为中心——互联网数仓主流）和 **Inmon**（3NF 企业级数仓，金融偏多）。**OneData** 是阿里体系的数据中台方法论：统一口径的指标体系（原子指标+修饰词+时间周期=派生指标）、统一的建模与开发规范、数据从"烟囱式"走向"公共层沉淀"。我实践里最受益的是它的**指标命名规范**（如 `sum_payment_1d`：聚合_原子指标_周期），口径冲突一看名字就能发现。

【追问链】你们的一致性维度是怎么保证的？（维度表统一出口 + 变更审批 + 总线矩阵维护）→ 原子指标和派生指标举例？（原子：payment_sum；派生：payment_sum_1d_pc；修饰词=终端，时间周期=1d）

### Q4. DWD 层怎么做到"一事一表"？清洗都洗什么？

【参考回答】一个 DWD 表对应一个**业务过程**（下单/支付/点击）的最细粒度事实。清洗五件事：去重（上游重复推送）、空值补默认、格式标准化（时间戳/枚举）、**脱敏**（手机号哈希——面试官大概率追问脱敏算法：MD5+盐 或 HMAC，要可逆场景用加密）、维度退化（把常用维度冗余进事实表减少 join）。**关键原则：不跨业务过程做 join**——那是 DWS/ADS 的事，DWD 保持"纯"。

【追问链】上游数据迟到/乱序怎么办？（ODS 按事件时间分区 + 允许 N 天迟到回补；实时侧 watermark）

### Q5. 维度建模中，事实表有哪几种类型？各自举例。

【参考回答】三种核心：**事务事实表**（一行一个业务事件，订单表）、**周期快照事实表**（一行一个周期汇总，每日账户余额表）、**累积快照事实表**（一行一个业务流程实例，列是各里程碑时间——订单从创建→支付→发货→完成，用于漏斗和时效分析）。加分项：**无事实事实表**（仅记录关系，如用户-页面曝光）、**迟到事实**（晚到的数据补录进累积快照的方式）。

【追问链】你的订单表是哪种？为什么？（事务；若做"履约时效分析"就再建累积快照，两表并存各有用途）

### Q6. 拉链表是什么？什么场景用？怎么实现？

【必问题，必须动手做过。本目录 `lab-数仓小实验/01-拉链表.sql` 有完整可运行实现。】

【参考回答】用**开始日期 + 结束日期**两列记录维度的历史版本，当前有效记录 end_date=9999-12-31。适用：**变化缓慢、需要回溯历史状态**的维度（用户等级、商品类目、组织架构）。优势：存储极省（只存变化）、任意"按当时状态"的历史查询支持。实现：每日增量与昨日全量对比（join 找出变化的 → 旧记录关链 end_date=当天-1，新记录开链 end_date=9999）→ 全量重写。**注意点**：执行幂等（重跑当天不能重复关链）、核心 key 上有更新无插入的边界（新用户直接开链）。

【追问链】变化频繁的维度能用拉链表吗？（不合适，快照式；或按"最近 90 天拉链 + 更早按月快照"冷热分层）→ 查某天全量怎么写？（`WHERE start_date <= 'X' AND end_date > 'X'`）

【动手印证】`lab-数仓小实验/01-拉链表.sql`——含 3 天增量、12 条断言的完整验证，亲手跑一遍比背十遍强。

## B. 维度设计（4 题）

### Q7. 缓慢变化维（SCD）三种类型？你们用哪种？

【参考回答】SCD1 只留最新（改覆盖）；SCD2 留全历史（新行，即拉链）；SCD3 留"当前+上一个"两列（极少用）。**实践**：分析价值高的属性（等级/城市/类目归属）用 SCD2，纯修正类字段（错别字）用 SCD1；一张维度表可以混用（列级声明）。**追问预警**：SCD2 的事实表关联要用"事件时间落在生效区间"的条件 join，不是等值 join——这是效率与正确性的平衡点（当天事实直接 join 当天快照，历史回溯才走区间）。

### Q8. 什么是一致性维度？为什么重要？

【参考回答】同一业务实体在所有事实表中**同一套定义、同一套属性、同一个物理出口**（如"用户维度"全局只有一张 dim_user）。价值：跨主题的报表可交叉、口径不打架；实现上靠**总线矩阵**（业务过程 × 维度的对照表）来规划。反面案例：A 组"活跃用户"和 B 组"活跃用户"过滤条件不同，董事会报表打架——这就是缺一致性维度的代价。

### Q9. 维度表里出现了两个"事实性"属性怎么办？（退化维度 / 阶梯维度）

【参考回答】概念题答两层：**退化维度**——订单号这种没有对应维度表、直接冗余进事实表的维度；**阶梯维度**——层级会变的维度（组织架构汇报线），用扁平化（每级一列）或桥接表解决，讲清桥接表的加权归因即可。再补" junk dimension"（一堆零散标志位合并成垃圾维度）能再加分。

### Q10. 大维度的存储和查询优化你们怎么做？

【参考回答】三招：**列裁剪与字典编码**（Hive/湖格式自带）；**维度表缓存/广播**（join 侧）；**分层冗余**——高频属性在 DWD 已退化，避免大维度 join 打满集群。极端例子：亿级会员表，按"常用属性子集 + 全量属性"拆冷热两张表。

## C. 指标体系与口径（4 题，二面高频）

### Q11. ★ 指标口径不一致怎么治理？

【面试官为什么问】这是数仓负责人 60% 的日常，答好了就是"能对一片领域负责"的证明。

【参考回答】治理四步：① **盘点**——把所有报表的同名指标扒出来对口径（一般能发现 30%+ 不一致）；② **收口**——指标定义唯一出口（原子指标+修饰词的命名体系），公共口径全部沉到 DWS 一张表；③ **机制**——口径变更走审批 + 影响面（血缘）自动通知下游；④ **验证**——口径变更后新旧双跑 N 天对比。**数字化表达**："治理前 43 个'活跃用户'口径，收敛到 6 个，报表对不上的工单从月均 20+ 降到 2。"

【追问链】业务坚持要自己的口径怎么办？（保留但打标签"业务自定义"，公共口径做基准）→ 怎么防止新增不一致？（新指标必须从指标平台选原子指标组合，禁止手写口径）

### Q12. 你们怎么做数据质量监控（DQC）？

【参考回答】按**四大质量维度**设计规则：完整性（行数波动、主键非空唯一）、准确性（值域/枚举/波动率对比昨日±阈值）、一致性（跨表对账：汇总=明细之和）、及时性（基线告警——任务未在 SLA 时间点完成即报警，比"失败才报"先进一代）。实现上分**强规则**（失败阻断下游）和**弱规则**（告警不阻断）。加分项：讲**基线管理**——大促前把核心链路的"最晚就绪时间"按小时分级设卡。

【追问链】规则误报多怎么办？（阈值分位数自适应 + 静默期 + 规则分级复盘机制）→ 出过质量事故吗？（准备一个真实案例：上游截断 → 下游报表错数 → 对账规则补上"行数突变即阻断"）

### Q13. 元数据和数据血缘有什么用？怎么落地？

【参考回答】血缘三层价值：**影响分析**（改这张表下游谁会炸）、**溯源**（报表数字从哪来）、**下线依据**（90 天无人访问的表可回收）。落地：任务级血缘从调度系统解析 SQL 依赖自动生成，字段级血缘用 SQL 解析器（如 Atlas/sqa 基建或自研 parser）；存储在元数据中心并与权限、成本系统打通。**加分**：我们用血缘做过一次"成本治理"——按"表产出成本 / 下游访问数"排优先级，下线了 200+ 无人访问表，月省 XX% 存储费用。

### Q14. 怎么向业务解释"数据为什么对不上"？给个流程。

【参考回答】标准排查五步（时间敏感，先口径后数据）：① 双方取数 SQL 摆出来对（八成是过滤条件/时间边界）；② 对齐口径（"GMV 含不含退款、含不含运费"）；③ 对齐时间切片（T+1 还是实时、时区）；④ 抽样对明细（找差异行）；⑤ 根因归类沉淀成 checklist。**这个题考沟通**：先说"我负责把它对齐"，再讲方法——姿态和方法一样重要。

## D. 数据回刷与幂等（3 题）

### Q15. ★ 历史数据要重算（回刷）怎么设计？

【面试官为什么问】回刷是数仓的"心脏手术"，做不好就是二次事故。

【参考回答】六要素：**影响面**（血缘圈出下游全表）→ **分区对齐**（重刷分区粒度与下游一致）→ **幂等**（全部 insert overwrite 同分区，禁止 append）→ **顺序**（按 DAG 拓扑逐层刷，就绪标记控制）→ **校验**（新旧双跑 diff 关键指标，diff=0 才切）→ **并行度与配额**（回刷任务单独队列，不冲击日常 SLA）。**故事收尾**：某次规则变更回刷 3 年数据，先刷 1 天验证 diff，再全量，X 小时完成，0 工单。

【追问链】下游有实时任务怎么同步回刷？（实时任务按天粒度可覆盖重写，跨天回刷要停写或引入修正流）

### Q16. 你的任务幂等是怎么保证的？

【参考回答】三层：写入用 `insert overwrite` 固定分区（天然幂等）；有状态计算用 checkpoint + 事务写（Flink 两阶段提交到 Kafka/湖表）；外部系统写走 upsert（主键幂等）。**红线**：任何"先 delete 再 insert"的手工操作都要平台化，人工跑批是事故之源。

### Q17. 上游表结构变更（加列/改类型）你怎么应对？

【参考回答】分级响应：加列（尾部加列兼容，DWD 同步加默认值）；改类型/语义（**破坏性变更**——走变更审批，血缘评估影响面，与上游约定双写过渡期）；枚举新增（DWD 映射表兜底 unknown）。平台化做法：schema 变更检查进 CI——上游 PR 自动跑血缘影响面报告。

## E. OLAP 与服务（3 题，2025–2026 增量考点）

### Q18. 明细/聚合查询越来越慢，你们怎么优化？

【参考回答】先定位再开药：**扫描量大** → 预聚合（DWS/物化视图）；**join 慢** → 大表建桶对齐 join（bucket join）；**点查/看板慢** → 把报表迁到 OLAP 引擎（Doris/StarRocks 的 Rollup/物化视图）；**并发挤兑** → 队列隔离（大查询专用资源组）。**选型口径**：高并发看板 → Doris/StarRocks；超大规模日志分析 → ClickHouse；湖上探查 → Trino/Spark SQL。数字示例：看板 P95 从 30s → 2s（DWS 沉淀 + 物化视图）。

### Q19. Doris 和 StarRocks 怎么选？（2025 高频选型题）

【参考回答】同源（StarRocks fork 自 Doris 早期）演化方向不同：**StarRocks** 在多表 join、湖查询（直接查 Paimon/Iceberg/Hive 外表）上更强，适合"湖仓查询加速"场景；**Doris** 社区生态大、版本节奏快、轻量易运维。我们的实践：已有 Paimon 湖 → StarRocks 直接加速湖上查询（免导数）；纯报表加速 → 两者都够，看团队熟悉度与社区支持。**面试原则：给"场景→选择"的映射，不要站队**。

【追问链】物化视图的刷新策略？（异步定时/事件触发，讲一致性代价）→ 湖查询和导数到内的权衡？（免导数省 ETL 但查询慢 2–5 倍；高频报表还是导数）

### Q20. 报表要秒级更新，离线链路扛不住，怎么办？

【参考回答】三级方案按成本递进：① 缩短调度周期（分钟级微批，简单但积压风险）；② **实时+离线双链路**（Flink 写实时明细/汇总，离线定时校准——Lambda 简化版）；③ **流批一体湖仓**（Flink+Paimon 分层，StarRocks 查询，一套模型两时效——详见 04 篇）。**决策依据**：时效价值 vs 维护两套逻辑的一致性成本，先算"延迟一天的业务损失"。

## F. 手撕 SQL 高频题型（3 题，现场白板/共享屏）

### Q21. 连续 N 天登录的用户怎么写？

【参考答案模板】核心：`row_number()` 打标法——按用户分组按日期排序，`date - rank` 得到"日期-序号"分组键，相同键即连续段，再对段聚合取 >= N。**讲完写法讲优化**：亿级用户先按月分区裁剪、只筛活跃用户子集；窗口函数换成 lag 比较 `datediff=1` 同样成立。**动手印证**：`lab-数仓小实验/03-连续登录.sql` 已验证。

### Q22. 留存率（次日/7 日）怎么写？

【参考答案模板】首访表 a（新用户×首访日）left join 活跃表 b on 用户 id and `b.dt = a.首访日 + N`，`count(b)/count(a)` 按首访日分组。**追问**：大表 join 怎么防倾斜？（两表都按用户 id 分桶对齐）→ 指标口径确认（"留存的活跃"用哪个口径——联动 Q11 治理话题，能接上就是亮点）。

### Q23. 每类商品销量 Top3 怎么写？（组内 TopN）

【参考答案模板】`row_number() over (partition by category order by sales desc) <= 3`；追问"并列怎么办"→ `rank()/dense_rank()` 的区别要讲清；追问"性能"→ 先 group by 到类目×商品粒度再开窗，避免明细级窗口。

## G. 进阶追问库（8 题）

### Q24. 元数据平台选型：Atlas / DataHub / OpenMetadata 怎么选？
Atlas：Hive/HBase 生态原生（Hortonworks 系），UI 与易用性一般；**DataHub**（LinkedIn 开源）： ingestion 连接器最全（60+）、血缘 API 好、社区活跃，当前主流首选；OpenMetadata：一体化（元数据+质量+治理），schema 稍新。**选型口径**：连接器覆盖你的组件列表 + 二开成本 + 社区响应速度。落地关键不是选型而是**自动采集**——手工维护的血缘必死。

### Q25. 数据分级分类怎么落地？
四步：定分级标准（如 L1 公开 / L2 内部 / L3 敏感 / L4 高敏——手机号、身份证、银行卡是 L4）→ 自动识别（正则 + NLP 扫描字段名与采样值，人工复核）→ 打标到列级元数据 → 权限/脱敏/审计按级联动（L4 默认拒绝、申请走工单）。**闭环**：新表创建时强制分级，未分级默认按 L3 处理。

### Q26. 实时数仓的建模和离线有什么不同？
三差异：① **粒度**——实时层通常不做太宽的明细（状态成本），保持窄事件流；② **维表**——离线 join 全量快照，实时必须处理版本（temporal join / 广播 changelog）；③ **回溯**——离线天然可回刷，实时要用湖表的增量读 + 重放。**一致点**：分层思想、一致性维度、指标命名全部复用——这是"流批一体建模"的根基。

### Q27. 大宽表膨胀怎么治理？
症状：一张 ADS 大宽表 200+ 列、20 个上游、每天 4 小时产出。治理：按"访问模式"拆——高频列保留、低频列回退到 DWS 按需 join；按"更新频率"拆——分钟更新和天更新拆两张表；用 OLAP 引擎（StarRocks 多表 join 快）替代"预 join 成宽表"的老办法。**判断标准**：宽表的列被引用率 < 20% 就该瘦身。

### Q28. 数据中台和数据仓库什么关系？
数仓是"技术资产"（分层模型 + 任务），中台是"服务体系"（数仓 + 统一指标/元数据/权限/成本的服务层 + 组织机制）。**务实回答**：别纠结名词，中台的本质是"数据能力复用的基础设施 + 组织保障"；很多公司失败在只建了技术没建机制（没有指标管理的 owner 与流程）。

### Q29. 作业级成本账单怎么实现？
三要素：资源消耗（YARN container 秒数 / K8s pod 资源秒数）× 单价 + 存储（表大小 × 副本 × 单价）+ 下游分摊（公共表成本按访问量分摊到业务）。落地：调度系统埋点 → 成本明细表 → BI 看板。**治理闭环**：月度红黑榜 + 回收机制（90 天无访问的表先下线访问再删数据）。

### Q30. 指标平台的技术方案怎么做？
组件：指标定义元模型（原子/派生/修饰词）+ 管理界面（口径审批流）+ 查询翻译层（指标 API → SQL 到对应物理表）+ 一致性校验。轻量起步方案：飞书表格管定义 + dbt/脚本翻译 SQL——**先有治理流程再有平台**，顺序反了就是给烂流程套壳。

### Q31. 你们怎么管理需求？数据团队被需求淹没怎么办？
机制题：① 需求分级（经营决策/常规报表/临时取数）不同 SLA 与资源；② **临时取数自助化**（SQL 自助平台 + 数据字典），把 60% 的取数需求从开发手里解放；③ 每月需求复盘（哪些需求做完没人用——反推需求准入）；④ 学会说"这个需求的代价是 X，业务确认要做"。

# 深挖补充（防问倒版）：细节与追问实录

## 深挖 1：拉链表的三个"进阶追问"标准答案

**追问 1："多个 SCD2 字段同时变化怎么办？"**
答：按"关键字段组合"判断是否开链——通常取**业务上重要的属性集**（等级+城市+归属）做变更检测；不重要的字段用 SCD1 原地更新。实现上 ods 增量与昨日快照按业务 key 对比"字段集合是否不同"，任一关键字段变化即关旧开新。

**追问 2："上游数据删除了，拉链表怎么处理？"**
答：三种策略按业务定——① 逻辑删除（加 is_deleted 标记，开一条 deleted 版本）；② 物理关链（end_date=变更日，查询自然消失）；③ 保留（不处理）。**关键在约定**：口径文档写明"历史事实表 join 拉链表后，被删用户的历史记录是否保留"——这决定的是财务口径，不是技术问题。

**追问 3："事实表怎么正确 join 拉链维表？"**
答：**当天事实 join 当天快照**（`dim.start_date <= fact.dt AND dim.end_date > fact.dt`）——左闭右开。性能优化：每天物化一份"当日生效"的维表快照（`CREATE TABLE dim_xxx_snapshot AS SELECT ... WHERE 当日有效`），事实表等值 join 快照表，避免高频区间 join。历史回溯才用区间 join。

**追问 4："拉链表跑错了怎么修？"**
答：因为整表重写（全量 delete+insert 模式）或分区覆盖模式实现而异——分区按天的实现（每日产出"当日全量快照 + 变化部分"）可以按分区重跑；全量重写式要回滚到前一天版本 + 从那天起重放增量。**所以拉链表的"每日增量"表必须永久保留**——它是重放能力的来源。

## 深挖 2：DQC 规则的完整分类表（面试可直接画）

| 维度 | 规则示例 | 强/弱 | 典型阈值 |
|---|---|---|---|
| 完整性 | 行数同比波动 <±30%；主键非空唯一 | 强（阻断） | 按表历史 P95 定 |
| 准确性 | 枚举值域校验、金额非负、波动率 | 弱→强 | 业务规则 |
| 一致性 | 汇总表 = 明细之和；跨表对账 | 强 | 差异=0 |
| 及时性 | 任务就绪基线（如 06:00 前核心表就绪） | 告警分级 | 大促分级设卡 |

**阻断设计**：强规则失败 → 下游任务调度自动冻结 → 告警到 owner → 人工修复后"重跑校验 + 解冻"。**没有阻断机制的质量规则只是报表**——这句话是资深分水岭。

## 深挖 3：指标体系的一个完整落地样例（口述可用）

以"支付金额"为例走 OneData 全流程：
1. **原子指标**：`payment_sum`（来源：DWD 支付事实表 amount 列，语义=成功支付金额，不含退款）；
2. **时间周期修饰**：`_1d`/_7d`/_30d`/`_ytd`；
3. **通用修饰词**：`_pc`（PC 端）/_app`/_all`；
4. **派生指标命名**：`payment_sum_1d_pc` —— 名字即定义；
5. **物理映射**：该指标 → `dws_payment_trd_1d` 表的 `payment_sum` 列（WHERE platform='pc'）；
6. **变更管理**：原子指标语义变更 = 全部派生指标变更，血缘自动通知 + 双跑校验。

**面试话术**："我们要求任何人聊'支付金额'必须落到指标平台的一个 ID 上——口头说'支付金额'在需求评审里是无效表达。"

## 深挖 4：回刷的依赖树切割实操

回刷最怕"一个任务重跑导致全公司任务连锁重跑"。实操三刀：
1. **血缘树剪枝**：只刷受规则影响的下游（字段级血缘的价值时刻）；未受影响的分支在调度系统上"挂起标记"；
2. **时间窗切割**：只刷受影响的时间分区（比如规则 2025-01 才生效，之前不动）；
3. **批次与就绪**：按层分批（DWD 全部完成才开 DWS），每批完成跑对账 diff，批次间人工确认点。
**停实时链路的决策点**：回刷的分区若被实时任务"覆盖写"会互相踩——约定"跨天回刷窗口内实时任务暂停/双写临时表"。

## 深挖 5：OLAP 排查一个慢查询的实操路径（以 Doris/StarRocks 为例）

1. `EXPLAIN` / `EXPLAIN ANALYZE` 看 plan：**扫描分区/桶数是否裁剪**（没裁 = 查询没带分区键或分桶键设计错）；join 是否走了 Colocate/Broadcast（变成 Shuffle/Partitioned 就慢）；
2. profile 看各算子耗时：scan 慢 → 存储裁剪/compaction/文件数；聚合慢 → 数据倾斜（看 instance 行数分布）；
3. 常见根因 Top3：查询没带分区键（改 SQL 或建 Rollup）、分桶键与 join 键不一致（重建表 Colocate）、实时导入未合并（等待 compaction 或强制）；
4. 兜底：物化视图固化高频模式。
