# 10 — 大厂日常工作实践（面试官默认你"在里面待过"的那套东西）

> 面试官区分"中型公司经验"和"大厂经验"，不看技术栈（大家都是 Spark/Flink），看的是**工作方式**：需求怎么来、变更怎么管、值班怎么值、事故怎么复盘、SLA 怎么保。这一篇把这套"隐性知识"显性化——面试中随口带出这些机制（"我们当时走的是基线监控，承诺时间前 2 小时预警"），比任何技术名词都更能证明你的层级。

## 一、数据研发全生命周期（大厂标准六阶段）

字节 DataLeap、阿里 DataWorks 都把研发流程固化为六阶段，每个阶段有平台卡点：

| 阶段 | 做什么 | 平台卡点（大厂特色） |
|---|---|---|
| **需求设计** | 需求评审（PRD+口径确认）、模型设计（选表/设计分区/评估资源） | 口径必须从指标平台选；模型设计文档进元数据中心 |
| **开发** | 写 SQL/作业，走 Git（大厂早已不走"平台里直接改"） | 代码规范 lint（SQL 静态检查：禁止 select *、必须有分区过滤） |
| **测试** | 数据正确性验证（双跑 diff）、性能验证 | 提交前自动跑冒烟（采样数据试跑 + DQC 规则预检） |
| **发布** | 走发布单：评审人（同组高阶）审批 → 推预发 → 生产 | **发布窗口**：离线任务禁止在 SLA 时段发布；实时作业需值班人知晓 |
| **验收** | 业务方确认数字、与旧口径双跑 N 天 | 验收不通过可一键回滚（任务历史版本 + 数据快照） |
| **运维** | 日常运维、监控响应、优化 | 基线监控自动接管（见下） |

**面试用法**：被问"你们怎么保证质量"时，别只说 DQC——把"六阶段 + 平台卡点"讲出来，立刻就是大厂工作方式。

## 二、SLA 与基线体系（大厂数据稳定性的核心机制）

**基线（Baseline）是阿里 DataWorks 的独创理念，字节 DataLeap 同款思想**：把有 SLA 要求的任务（如"老板晨报 8:00 前必须出"）加进基线，设**承诺时间**，平台根据依赖链上下游任务的运行情况**预测产出时间**，预测会违约时**提前报警**（而不是失败后才报）。

**一个真实基线的构成**：
- 保障任务：老板晨报表（ADS 层）
- 承诺时间：08:00
- 预警余量：提前 2 小时（06:00 预测完不成就报警）
- 报警对象：值班人 + 任务 owner + 上游链路 owner

**基线的日常价值**：某天上游一个不重要的任务变慢 20 分钟，链路预测显示"晨报将 08:15 产出"→ 06:00 报警 → 值班人还来得及扩资源或手动并行。**没有基线的公司，是 08:10 发现老板看不了晨报才开始排查**——这就是数据稳定性治理的分水岭。

**分级**：基线按重要性分级（P0 营收数据 / P1 核心业务 / P2 一般报表），大促期间 P0 基线"禁止发布、专人盯守、资源独占"。

【面试话术】"我们 SLA 任务基线覆盖率 80% 以上，上季度基线违约 0 次；有次上游抖动，基线提前 2 小时报警，值班扩了资源，业务无感。"——一句话三个信息（覆盖率、结果、事例），全是机制。

## 三、值班与应急响应（On-call）

**轮值机制**：每周轮换 primary/secondary；值班职责 = 告警响应（15 分钟内 ack）+ 每日巡检（基线状态/关键指标/资源水位）+ 值班日志。

**告警分级与响应**：

| 级别 | 定义 | 响应要求 |
|---|---|---|
| P0 | 营收数据错误/核心报表不可用/数据安全事故 | 立即响应，1 小时内止损，拉群升级到 leader |
| P1 | 核心链路延迟超基线/重要作业失败 | 15 分钟 ack，当班处理 |
| P2 | 一般作业失败（有重试余量）/资源水位 | 当天处理 |
| P3 | 优化建议类 | 周会看 |

**应急 SOP（先止损后定位）**：告警 → 确认影响面（哪些基线受影响）→ **止损决策**（重跑/降级/切备份链路——宁可给错日期的口径声明，不给错数）→ 定位根因 → 复盘。

**复盘模板（大厂标准四段，背下来）**：
1. **时间线**：发生/发现/响应/止损 各时点；
2. **影响面**：受影响基线、业务方、数据范围；
3. **根因**：5-Why 到机制层（不是"人手滑"而是"为什么手滑能直接生效"——缺审批/缺预发）；
4. **Action 项**：每条有 owner 和 deadline，下次值班 review。**大厂复盘文化：对事不对人，惩罚机制只针对"绕过流程"**。

【面试必考】"讲一次 P0 事故"——按这个模板讲，时间线里要敢写自己的失误（"我发布的变更没走预发"），复盘落在机制补齐——这是大厂文化的标志性回答。

## 四、变更管理（数据侧的"发布工程"）

变更三类，管控强度不同：
- **代码变更**：Git + 发布单 + 同组高阶评审 + 预发验证；SQL 的 review 要点：分区过滤、幂等写法、资源预估、口径来源；
- **数据变更**（回刷/订正）：回刷单（影响面血缘自动生成 + 双跑 diff + 分批执行）——见 02 篇 Q15；
- **配置变更**（调度周期/资源/依赖）：变更单 + 基线影响评估（改依赖可能破坏别人的基线！）。

**大厂红线**：生产环境禁止手工操作（任何手工 SQL 都要走工单留痕）；高危操作（drop/全表 update）平台级禁用。**面试金句**："我们平台直接禁用了 drop，想删表走审批——不是相信人，是不给人犯错的机会。"

## 五、日常协作模式

- **与产品**：需求评审前先对齐口径（"日活"的定义在指标平台有没有）；拒绝需求的方式是给代价（"这个实时口径要多一条链路，月成本 X，业务确认要做"）；
- **与算法**：特征表服务——约定特征口径、更新频率、point-in-time 正确性（防止特征穿越——训练时用了未来数据）；
- **与后端**：数据服务 API 的 SLA 与限流；大表导出的批量协议；
- **与业务方**：培训自助取数工具、数据字典维护、周期性"数据开放日"答疑。

**沟通心法**：数据团队是"服务平台"，不是"需求池"——用自助化消灭低价值需求，用机制管理高价值需求。

## 六、大厂工具链地图（面试能对上号）

| 公司 | 平台 | 特色 |
|---|---|---|
| 阿里 | DataWorks（OneData 体系） | 建模方法论 + 智能基线 + 数据地图，商业化最成熟 |
| 字节 | DataLeap | 全链路智能基线监控（依赖拓扑 BFS 预测违约）、SLA 保障平台、数据资产治理 |
| 美团 | 数据平台系（快车/集团统一） | 落地细节与数据敏感性著称 |
| 腾讯 | WeData | 一站式研发治理 |
| 快手/百度/京东 | 自研系 | 各有侧重（资产治理/湖仓一体） |

**面试用法**：没在这些公司待过没关系——被问"你们用什么平台"时，说自建/开源组合（调度 DolphinScheduler + 开发 IDE + 元数据 DataHub + 质量 Griffin/自研），**然后主动对比大厂平台的机制**（"我们缺基线预测，用调度系统插件补了个简化版：预测任务链路完成时间"）——这段话证明你既懂大厂标准又能落地。

## 七、大厂定级与晋升逻辑（对应你的 40k–50k）

| 级别 | 阿里/字节参照 | 期望画像 | 典型薪资月 base |
|---|---|---|---|
| 执行层 | P5 / 1-1 | 给明确需求能高质量完成 | 20k–30k |
| **独当一面** | **P6 / 1-2** | **独立负责一个业务域的数仓/链路，有质量事故预防意识，能带新人** | **30k–45k** |
| **领域负责** | **P7 / 2-1** | **对一片领域（实时数仓/平台/治理）负全责，有架构决策与跨团队推动** | **45k–70k** |

**你的 40k–50k 落在 P6 尾–P7 头**：面试必须展现"领域负责"的证据——不是做了多少个需求，而是**机制建设**（你建的基线/规范/工具在你不在线时也在工作）。面试官问"这个事情是你做的还是团队做的"，真正想听的是"我的角色是什么、我推动了什么改变"。

**晋升材料思维**：大厂晋升答辩 = " Impact 论"——一个问题（多大范围多痛）→ 一个方案（为什么是你做、为什么这么做）→ 一个结果（量化）→ 一个沉淀（机制/工具/文档，别人在复用）。**面试时的项目描述就应该按晋升材料组织**——这也是 09 篇自我介绍的骨架。

## 八、入职前 90 天行动清单（面试官问"入职后打算怎么做"的标准答案）

- **前 30 天（听与看）**：跑通现有链路全流程；读数仓模型与口径文档；记下所有"看着不合理"的点（先别改）；与上下游各聊一次（产品/算法/后端最痛的问题）；接手值班。
- **31–60 天（小胜）**：修 3 个看得见的痛点（一个慢任务/一个缺失告警/一个口径混乱）；建立自己的基线视图；产出第一份文档（如"当前链路风险清单"）。
- **61–90 天（方案）**：针对 30 天记录的不合理点，提 1 个有 ROI 的改进方案（影响面/成本/收益），推动立项。
**面试话术**："我不会上来就改东西——先证明我理解现状，再用小胜利建立信任，最后才推大方案。"（这段话本身就会让面试官点头。）

## 九、日常 Checklists（可直接抄）

**每日巡检（值班 10 分钟）**：
- [ ] 基线状态：全部绿色？黄色预警的谁在处理？
- [ ] 昨日核心任务：失败/重跑/延迟 TOP3
- [ ] 资源水位：队列/集群/存储异常增长
- [ ] DQC：强规则阻断项
- [ ] 实时作业：checkpoint 成功率、消费 lag、反压

**上线前 checklist**：
- [ ] 预发环境双跑 diff=0
- [ ] 影响面（血缘下游）已通知
- [ ] 资源预估已审（不会挤爆队列）
- [ ] 回滚方案（历史版本 + 数据快照）
- [ ] 上线时间不在基线高危时段
- [ ] 发布单审批完成

**大促保障 checklist（T-14 天起）**：
- [ ] 流量预估与容量扩容完成
- [ ] 基线分级调整（P0 清单确认）
- [ ] 冻结发布窗口公告
- [ ] 应急预案演练（杀节点/断上游/降级）
- [ ] 值班表与升级路径
- [ ] 预口径 vs 精口径双版本确认

## 十、周报怎么写（结果导向，面试聊到"怎么汇报"用）

反面："本周完成了 3 个需求，处理了 2 个告警。"
正面："① 本周交付 X 域 3 张核心表，基线内就绪（承诺 08:00，实际 06:40）；② 治理：下线 12 张无访问表，月省存储 X%；③ 风险：实时链路反压 1 次，已定位为 sink 批量不足，下周一优化。——三条分别是：交付、治理、风险，全部带数字。"
**原则**：只写结果与风险，不写过程；数字优先；风险要带方案。
