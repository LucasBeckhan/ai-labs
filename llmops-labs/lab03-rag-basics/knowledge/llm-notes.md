# LLM 推理与 LLMOps 学习笔记（来自本仓库实验验证结论）

## 模型与量化
量化把模型权重从 FP16（每参数 2 字节）压缩到 Q4（约 0.5 字节/参数），体积与显存近似线性缩小、精度损失很小。0.5B 模型 FP16 约 1GB，Q4 后约 400MB，笔记本可跑。KV Cache 显存随 token 数线性增长，是长上下文与高并发的主要成本来源。

## 推理参数
temperature 缩放 logits 分布（0 是贪心解码，越大越发散）；top_p 按累积概率截断候选。抽取、分类、SQL 生成等任务用低 temperature 求稳定，创意生成用高值求发散。token 是成本与限流的计量单位，chat/completions 响应的 usage 字段包含 prompt_tokens 与 completion_tokens。

## AI 网关
统一协议（OpenAI 兼容格式是事实标准）、模型别名路由（应用只认别名，后端随时替换）、虚拟 key（按团队/项目发放，带 RPM/TPM 限流与预算控制）、用量观测（token 与费用归因）。虚拟 key 必须落数据库（PostgreSQL），网关本身无状态可水平扩展。

## RAG
链路：文档 → 分块 → 嵌入 → 向量库 → 检索 top-k → 拼 prompt → 生成。中文场景应选择中文或多语言嵌入模型（如 bge-m3），查询与文档必须用同一个嵌入模型。块大小与检索条数 TOP_K 是最重要的两个旋钮：块太大稀释语义、太小丢上下文；TOP_K 过小漏掉关键块、过大引入噪声并增加成本。

## 评估
检索命中率（Recall@k）反映数据质量；忠实度反映生成是否只基于检索内容；越界拒答测试防幻觉。指标要分层看：检索失败换数据策略，生成失败换模型或 prompt。文档级召回 100% 不代表块级命中，评估粒度要下沉。

## Text2SQL 与 Agent
schema 必须注入 prompt；安全三件套是只读数据库账号、SQL 白名单校验、强制 LIMIT 与超时。执行报错可以回传给模型重试，但小模型可能重复犯同一个错，此时优先尝试 few-shot 示例而不是升级模型（成本更低）。

## 微调
LoRA 冻结基座、只训练低秩 adapter 矩阵，参数量降到 1% 以下。微调改变行为与格式，不擅长注入知识（知识用 RAG）。训练数据质量决定效果上限，留出集用于防过拟合。

## 推理服务生产化
vLLM 的两大机制：PagedAttention（KV Cache 分页管理，消除预分配碎片）与连续批处理（新请求任意时刻插队）。显存估算方法：权重 = 参数量 × 每参数字节数；KV Cache = 2 × 层数 × 隐藏维度 × 2 字节 × token 数。K8s 上 GPU 通过 device plugin 成为可调度资源，GPU 节点打污点防普通任务抢占。
