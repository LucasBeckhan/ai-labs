## 核心问答

**Q1：RAG 的完整链路是什么？每一步的质量瓶颈在哪？**

> 参考答法：离线链路：文档 → **分块**（块太大稀释语义、太小丢上下文）→ **嵌入**（把文本变成向量，质量取决于嵌入模型）→ 入向量库。在线链路：问题嵌入 → **向量检索**（top-k 最近邻，可加混合检索/重排）→ 拼 prompt → LLM 生成。瓶颈多数在数据侧：分块策略、嵌入模型与语言匹配度、检索召回率 —— 本实验会亲眼看到"检索没命中，模型再聪明也答不出"。

**Q2：为什么嵌入模型的选择很重要？**

> 参考答法：嵌入模型决定"语义相近的文本向量是否相近"。中文场景用英文模型（如 MiniLM）召回会明显变差；本实验用 bge-m3（BAAI 的多语言模型，通过 Ollama 提供嵌入服务）。另外注意**查询和文档要用同一个嵌入模型** —— 用不同模型算的向量不在一个空间里，检索必然失败。

**Q3：向量库解决什么问题？和传统检索什么关系？**

> 参考答法：向量库做**近似最近邻（ANN）检索** —— 在百万级向量里毫秒级找到 top-k 相似项（HNSW 索引）。它解决"语义找得到"（"自动扩缩容"能匹配到"HPA"），传统倒排索引解决"关键词找得到"。生产常用混合：BM25 + 向量双路召回再融合。本实验用 chromadb（嵌入式，零部署，适合本地/原型；生产参考 Milvus/pgvector/Elasticsearch）。

### 2. 关键实验：TOP_K 对答案质量的影响（本实验灵魂）

用评估集里的同一批问题（如 `Spark executor 是怎么启动的？`），只改 TOP_K（脚本顶部常量），跑 Lab 04 的评估脚本对比：

- **TOP_K=3（默认）实测**：忠实度 3/5（60%）—— 部分问题的关键块没进上下文，模型要么漏要点、要么老实说不知道。注意 LLM 输出有随机性：同一问题同一参数，不同次运行可能一个对一个错 —— **单次评估有噪声，结论要多跑几轮再下**。
- **TOP_K=6 实测**：忠实度 4/5（80%）—— 关键块进入上下文的比例提高，回答更完整。

```bash
# 复现：临时改 TOP_K
LITELLM_LOCAL_MODEL_COST_MAP=True ../.venv/bin/python -c "
import sys, rag_demo
rag_demo.TOP_K = 6
sys.argv = ['x', 'Spark executor 是怎么启动的？']
rag_demo.main()"
```

> **这就是为什么"没有评估就没有 LLMOps"**（Lab 04 的引子）：不建评估集，你根本不知道 TOP_K 该是 3 还是 6，也不知道换分块策略是变好还是变坏。所有 RAG 优化都必须拿评估数据说话。

## 观察与思考

1. 看 `chroma_db/` 目录 —— 向量库是**持久化文件**，删除它等于重建索引。重复运行脚本为什么只增量处理？（脚本按 source 统计已有块数）
2. 检索结果里的"距离"是什么？（向量距离，越小越相似；0.5 上下在本实验就是"弱相关"的灰色地带 —— 重排序模型 reranker 的用武之地）
3. 0.5B 的模型做 RAG 生成够吗？（简单总结够用；复杂多跳推理不行。生产常见分工：小模型做路由/抽取，大模型做最终生成 —— 又回到 Lab 02 的路由）

## 常见坑

- chromadb 的 OllamaEmbeddingFunction 需要 `pip install ollama`（python 包，实测踩过）
- 用 litellm SDK 调自己的网关，model 必须带 `openai/` 前缀（`openai/qwen-small`），否则 SDK 会去猜 provider 报错（实测踩过）
- **生成调用务必设 `max_tokens`**：实测不设上限时 0.5B 小模型可能陷入无限生成（单次跑出 1.8 万 token），卡死整条流水线
- 中文分块别按英文 token 估算长度：本实验按**字符数**切（400 字符 ≈ 200~300 汉字）
- 改了 CHUNK_SIZE 后要删掉 `chroma_db/` 重建索引，否则新旧块混在一起
