# 工单会话与客户上下文：可恢复记忆

> 建议 4小时，完成后提交自己的实现和证据。所有业务数据为虚构；原 README/脚本提供机制参考，本页是新增业务必做练习。新版总入口：[业务路线](../CURRICULUM.md)。

## 业务输入与完成边界

同一值班人员追问“刚才上海那条线路呢？”系统要记住工单中的 circuit_id，却不能把其他客户、其他工单的信息带进来。

先回答：谁发起？要解决什么问题？允许读什么？哪些动作要人工确认？缺数据如何结束？这五项写入 work/README.md 后再编码。

## 从空白手写的任务

1. 写 work/session_store.py，用 SQLite 保存 (tenant_id,actor_id,session_id) 联合隔离的会话；字段包含 updated_at、version、expires_at、facts、evidence_refs。不要仅用 session_id 做主键。
2. 分清消息历史、业务事实、任务状态、长期偏好：链路状态有时效，不能永久记为事实；偏好只存经用户确认的非敏感内容。
3. 摘要前后均保留 evidence id、时间、待确认标记和未完成步骤；用显式 facts schema，不能把模型生成的推测升级为已确认事实。
4. 写压缩测试：前10轮确定 C-A01，第11轮追问；摘要必须保留资产和租户，但失效观测需要重新查询。实现 TTL 到期后“不知道/需重查”的路径。
5. 设计两个并发请求更新同一会话，用 version 条件更新检测冲突，不允许最后一次写悄悄覆盖；结束进程后重启读取，验证 SQLite 中的任务与事实仍可恢复。
6. 对长期记忆实现删除路径；缓存键至少包含 tenant、用户权限范围或权限版本、数据版本、query，避免跨租户和撤权后复用。

## 运行入口与参考边界

使用标准库 sqlite3/tempfile/unittest，数据库放 work/，每个测试创建独立临时库。产出自己的 memory 测试；原 memory_agent.py 只用于观察上下文压缩，不作为持久化实现。

模型阶段不限定框架。优先沿用原有模型网关适配器，但密钥从环境/Secret获取，不复用旧例子中的硬编码演示值。离线FakeModel验证控制逻辑，真实模型验证工具选择和回答质量，两者分别报告。

## 故障与验收

demo-a/demo-b 使用相同 session_id 仍隔离；过期观测不进入当前结论；两次并发写有冲突反馈；进程重启后不丢待办状态；删除后重查无记录。

每个故障保存：输入、身份、关键trace、错误码、根因、最小修复、恢复结果、预防措施。对照 [生产故障表](../business/FAILURE-DRILLS.md)，不要把单纯重跑成功当修复。
