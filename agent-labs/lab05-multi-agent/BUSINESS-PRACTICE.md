# 跨网络、云与安全的协同诊断

> 建议 4小时，完成后提交自己的实现和证据。所有业务数据为虚构；原 README/脚本提供机制参考，本页是新增业务必做练习。新版总入口：[业务路线](../CURRICULUM.md)。

## 业务输入与完成边界

客户说“应用访问慢”，可能涉及链路、云资源或安全策略。这里训练三类观察结果的融合，不假设公司真实系统已具备这些 API。

先回答：谁发起？要解决什么问题？允许读什么？哪些动作要人工确认？缺数据如何结束？这五项写入 work/README.md 后再编码。

## 从空白手写的任务

1. 为网络、云资源、安全告警各写一份模拟结果，统一 observed_at、scope、evidence_id、confidence、missing 字段。加入“网络正常但云 CPU 高”与“时间窗口不同、证据冲突”两例。
2. 先写固定 Workflow：并行采集3类证据→规则识别缺口→汇总。再写单 Agent 自选工具。最后才实现 Planner/Executor；三者使用相同数据和成功标准。
3. Planner 只允许分配有注册工具的任务；工具权限、租户和总预算不能被计划覆盖。Executor 产出证据包，Summarizer 只能引用包内信息。
4. 某一路 timeout 时返回 partial，指出缺少哪类证据；另外两路不得被丢弃，也不得把失败当成无异常。对冲突不能简单多数投票，要按观测时间/来源提出待验证项。
5. 记录每种方案每题模型调用数、总token、时延和成功率。若多 Agent 没有收益，结论可以是不采用；不要为了“架构先进”而增加角色。
6. 如做并发，给任务分配稳定 task_id，避免多个 Executor 写同一字段；共享 Python dict 不等于持久化或跨进程一致性。

## 运行入口与参考边界

用 FakeModel 固定 Planner 输出测试执行边界，再接真实模型评估；不要求本课程自身启动多个工作代理。原 planner_executor.py 只示范角色拆分，业务实验需自己补全失败状态和证据结构。

模型阶段不限定框架。优先沿用原有模型网关适配器，但密钥从环境/Secret获取，不复用旧例子中的硬编码演示值。离线FakeModel验证控制逻辑，真实模型验证工具选择和回答质量，两者分别报告。

## 故障与验收

同一输入在三种方案中事实口径一致；网络正常不意味着应用正常；单路失败标 partial；最终不能无证据认定安全攻击或承诺修复。提交至少6种场景对照表。

每个故障保存：输入、身份、关键trace、错误码、根因、最小修复、恢复结果、预防措施。对照 [生产故障表](../business/FAILURE-DRILLS.md)，不要把单纯重跑成功当修复。

## 提交与评分

提交 work/代码、配置、可复跑测试、结果JSON/日志和一页复盘。业务正确30分、边界与失败处理30分、手写与测试25分、复述取舍15分；80分通过，越权/无审批写入/敏感数据泄露直接重做。引用和数值须与fixture一致；未运行部分标记未验证。
