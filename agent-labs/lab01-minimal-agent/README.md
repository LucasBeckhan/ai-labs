## 核心问答

**Q1：Agent 和普通的 LLM 调用有什么本质区别？**

> 参考答法：普通调用是"一问一答"；Agent 是**把 LLM 放进循环里**：模型输出决定下一步动作（调用工具/给最终答案），工具结果回流给模型再决策，直到任务完成。三个要素：**循环、工具、记忆（历史）**。框架只是把这个循环工程化（加上状态管理、重试、并发等）。

**Q2：为什么用 prompt 输出 JSON 而不是原生 function calling？**

> 参考答法：① 教育价值——亲手实现框架在底层做的解析与修复；② 通用——任何模型可用（0.5B 也行），不依赖模型支持 tool_calls；③ 可控——解析失败时我自己决定重试策略。生产上模型支持原生 tool calling 时用它更稳（结构化输出更可靠），但原理一模一样。

**Q3：小模型做 Agent 的经典失败模式是什么？怎么治？**

> 参考答法：本实验**实测实录**：① 格式崩坏（输出 markdown/单引号 JSON）→ 解析器剥壳 + 容错 + 失败反馈重试；② **死循环**——拿到工具结果后不切换 final_answer，反复调用同一工具 → **循环检测**（记录已执行的工具调用与结果，重复时不执行、直接把结果和明确指令塞回去）；③ 幻觉工具名 → 校验 + 告知可用清单；④ 兜底 max_steps。这套组合拳就是"小模型也能跑 Agent"的工程秘密。

## 实测实录（本机真实运行记录，最有价值的一节）

**第一版运行**（无循环检测）——0.5B 模型的死循环原样呈现：

```
任务: 算一下 23 乘以 47 再除以 2
步骤1: calculate('23*47/2') → 540.5      ← 工具调用正确！
步骤2: calculate('540.5')    → 540.5      ← 模型把结果又当成算式
步骤3~6: 反复 calculate('540.5')          ← 死循环，6 步耗尽
结果: 任务未完成
```

**加入循环检测后**——同样的模型、同样的任务：

```
步骤1: calculate('23*47/2') → 540.5
步骤2: calculate('540.5')   → 540.5
步骤3: calculate('540.5')   → ⚠️ 检测到重复调用，注入纠偏提示
步骤4: {"action": "final_answer", "answer": "540.5"}   ✅ 完成
```

三个测试任务全部达成：`540.5` ✓、`中文字数=12` ✓、K8s 直答 ✓（第三个任务模型先多调用了一次无关工具——小模型的"过度行动"倾向——但循环检测同样把它拉回了正轨）。

> **面试金句**："我实测过 0.5B 模型跑 Agent 会陷入重复调用死循环，加了 20 行循环检测（重复的工具调用不执行、直接把结果和指令塞回上下文）就稳定了——Agent 的可靠性是工程治理出来的，不是模型白送的。"

## 核心问答

**Q1：Agent 和普通 LLM 调用有什么本质区别？**

> 答：普通 LLM 调用是单轮问答，Agent 是**循环执行**的决策系统。核心差异在于 Agent 有三个能力：
> 1. **工具调用**：能调用外部 API、数据库、搜索引擎
> 2. **状态记忆**：能记住之前的对话和工具返回结果
> 3. **决策循环**：根据当前状态决定下一步动作（调用工具/继续思考/给出答案）
>
> 本实验实现的就是最小循环：`思考 → 决定调工具 → 执行工具 → 观察结果 → 再思考`，直到模型认为可以给出最终答案。

**Q2：为什么循环检测很重要？实测中发现了什么问题？**

> 答：小模型（0.5B）容易陷入"重复调用同一工具"的死循环。本实验实测发现：
> - 模型调用 `calculator("2+3")` 得到 5
> - 又调用 `calculator("2+3")` 得到 5
> - 继续调用...永远停不下来
>
> 解决方案是维护一个 `called_tools` 集合，检测到重复调用时强制跳出循环。这是生产环境 Agent 的必备护栏。

**Q3：ReAct 框架的"Reasoning"和"Acting"分别指什么？**

> 答：ReAct = **Re**asoning + **Act**ing
> - **Reasoning**：模型思考当前状态、决定下一步动作（输出在 `<think>` 标签内）
> - **Acting**：模型执行工具调用（输出 `<tool_call>` 标签）
>
> 本实验简化了 ReAct，没有显式分离 Reasoning 和 Acting，但核心循环思想一致。完整的 ReAct 实现会让模型先输出推理过程，再输出动作，便于调试和理解模型决策逻辑。
