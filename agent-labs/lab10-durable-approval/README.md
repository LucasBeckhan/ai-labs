# Lab10：持久化、人工审批与重复执行

> 约6小时。前置Lab03/08/09。所有“发布”只写本地模拟表，不发送消息、不修改设备、不连接公司工单系统。

## 业务任务

安全周报草稿需要审核后才能模拟归档；网络排查助手只能生成变更建议。用户点批准后服务进程可能重启、网关可能重复回调，审批必须绑定到同一份内容，不能再次误执行。

## 手写数据与状态（90分钟）

在work/写SQLite实现，建表runs、steps、approvals、outbox、audit。任务主键与查询必须包含tenant；幂等键至少覆盖tenant+业务单号+版本+动作。敏感数据不保存到普通日志。

```text
queued → collecting → drafting → awaiting_approval → approved → completed
             ↘ failed/partial        ↘ rejected/expired
```

持久化当前状态、版本、已完成步骤和工具结果引用，不能只存在Python字典。状态迁移用事务与version比较更新。审批记录包括proposal_hash、actor、scope、expires_at、decision；由已认证身份写入，不让模型自己批准。

## 审批与幂等（90分钟）

1. 对规范化草稿计算hash，审批只针对该hash和动作；任何内容改动都让旧审批失效。
2. 执行前再次检查身份、租户、权限、期限和当前版本，避免审批时允许、执行时已撤权。
3. 模拟动作只写mock_published_reports表；以唯一业务键阻止重复。两个worker抢同一任务时至少一个应获得明确冲突/已完成结果。
4. 模拟本地事务中“更新状态+写outbox”一起提交。实际外部系统不能与本地SQLite共用事务；需要幂等接口或查询确认/对账，不宣称exactly-once。
5. 若外部响应丢失，状态为unknown，先查询原业务键是否已完成再重试；没有查询能力就转人工核实。

## 中断恢复演练（90分钟）

写可控crash_point，在以下位置raise异常或结束测试进程；重启后读取数据库，不重放整个原始对话。

| 中断点 | 恢复要求 |
|---|---|
| 取证后、草稿前 | 保留证据和完成步骤，可从草稿继续 |
| 等待审批 | 重启后仍等待，不默认为批准 |
| 审批后、模拟发布前 | 重查授权、hash和过期时间 |
| 已模拟发布、未返回响应 | 重试不会多一条归档 |
| 内容改动后复用旧审批 | 拒绝执行，要求新审批 |
| 另租户访问相同run_id | 不泄露任务是否存在与内容 |

测试必须打开同一路径数据库的新连接或新进程，不能只在同一对象上调用两次冒充“重启”。将业务时钟作为依赖注入，测试过期不使用长sleep。

## 交付与验收

提交migration.sql、状态机代码、至少上述6类测试、两worker竞争测试和恢复前后表记录。重复提交同一业务动作最终只产生1条模拟归档；无审批不得执行、审批过期不得执行、改内容必须重审。失败路径非零退出且可追溯。

将此模块接到Lab09时，审批前只能展示草稿；接Lab08时API返回任务ID和状态，接口重试不能重新创建同一任务。真实工单/邮件/网络变更接入属于后续授权项目，不是本实验默认动作。
