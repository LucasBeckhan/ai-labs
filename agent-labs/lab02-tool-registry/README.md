## 核心问答

**Q：这一层的意义？**

> 答：OpenAI tools API、MCP（Lab 06）、LangChain Tool 都用同一套"名字+描述+JSON Schema 参数"的工具规范。本实验手写注册表后，所有框架的工具系统你都看得懂了；而且掌握了**两层防线**：Schema 校验（机器可读契约）+ 范围裁剪（代码层 min/max 兜底，如密码长度 6-32）。

## 实测实录（两个新故障 + 治理）

**故障 A：parse_error 死循环（回显破坏）**
模型正确生成了密码 `9qh6...`，但把含特殊字符的密码回显进 JSON 时反复破坏格式 → 连续 parse_error。
治理：**连续 2 次格式错误且已有工具结果 → 降级直接返回工具结果**（生产模式的优雅退出）。

**故障 B：绕过专用工具、自己"心算"公式**
温度转换任务，模型不用 `c_to_f` 工具而是调 `calculate` 拼 `37.5*1.8+37.5`——公式还拼错了（正确是 ×1.8+32）。
治理：① 工具描述写得更"诱人"（描述里直接给公式）；② 更强的模型（qwen-strong）；③ 关键计算不让模型自由发挥——**专用工具的存在就是为了让模型别自己算**。

> **面试金句**："Agent 的工具选择本身就是幻觉高发区——模型会绕过你精心写的工具自己拼算式。治理手段是描述工程 + 专用工具优先 + 结果校验，而不是指望模型'听话'。"

## 核心问答

**Q1：工具注册机制的本质是什么？为什么要用装饰器？**

> 答：工具注册的本质是**建立函数到元数据的映射**。装饰器 `@register_tool` 做的事情：
> 1. 从函数签名提取参数类型（通过 `inspect.signature`）
> 2. 生成 JSON Schema（描述参数名、类型、是否必填）
> 3. 从 docstring 提取工具描述
> 4. 把函数对象和元数据存入全局注册表
>
> 用装饰器的好处是**声明式**：工具定义和使用逻辑分离，新增工具只需加一个装饰器，不需要改注册逻辑。这和 Flask 的 `@app.route` 是同一个设计模式。

**Q2：JSON Schema 在工具调用中扮演什么角色？**

> 答：JSON Schema 是**模型和工具之间的契约**。它告诉模型：
> - 这个工具需要什么参数（参数名、类型）
> - 哪些参数是必填的（required）
> - 参数的含义（description）
>
> 模型根据 Schema 生成符合格式的 JSON，我们的代码再根据 Schema 验证和解析。如果 Schema 不清晰（比如缺少 description），模型可能生成错误的参数名或类型。实测发现：参数描述越具体，模型的调用准确率越高。

**Q3：如何处理工具执行失败？为什么错误信息要返回给模型？**

> 答：工具失败时必须**把错误信息作为观察结果返回给模型**，而不是抛异常。原因：
> 1. 模型可能根据错误信息调整策略（比如换个搜索词）
> 2. Agent 的循环不应因单个工具失败而中断
> 3. 这是 ReAct 框架的核心：Observe 阶段包括成功和失败的观察
>
> 实现方式：`try-except` 捕获异常，把 `str(e)` 作为工具返回值。本实验的 `execute_tool` 函数就是这么做的。

**Q4：本实验发现的两个故障有什么工程启示？**

> 答：
> - **故障 A（parse_error 死循环）**：说明 Agent 需要**降级机制**。当模型输出格式反复出错时，不能无限重试，要设置阈值后降级到"直接返回工具结果"。
> - **故障 B（绕过工具自己算）**：说明模型有"过度自信"倾向，会用通用能力替代专用工具。治理方法是**让工具描述更诱人 + 结果校验**，而不是指望模型"听话"。
>
> 这两个故障在生产环境很常见，解决方案体现了 Agent 工程的两个核心原则：**优雅降级**和**防御性编程**。
